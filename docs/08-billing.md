# 08 计费与结算

## 1. 价格

所有倍率都相对**官方价**，即 sub2api 内置价目表中的模型价格（美元国际版标价）。sub2api 对每次请求计算出的 `total_cost` 就是按官方价算出的费用。

| 符号 | 含义 | 谁设定 |
|---|---|---|
| m_s | 寄售卖家倍率 | 卖家，在平台允许的区间内（区间按厂商由管理员配置） |
| c | 抽佣率 | 管理员，第一期为全局固定值 |
| p = m_s × (1 + c) | 买家指定该卖家时的价格，即寄售专属分组的倍率 | 自动计算 |
| D | 默认分组售价倍率 | 管理员，按默认分组设定 |
| m_b | 回收倍率 | 平台报价引擎，卖家接受后生效 |

**约束**

- 回收报价必须满足 m_b ≤ D × (1 − 最低毛利 − 安全缓冲)，否则平台在默认分组里亏钱。
- 寄售卖家进默认分组需要满足同样的条件（m_s 代入），不满足时仍可在市场上被指定。

**国产模型的官方价口径**：sub2api 内置的 GLM、Kimi、MiniMax 等价格是国际版美元标价，与国内人民币标价不同（sub2api 代码注释中已说明采用国际版）。卖家门户要直接展示这张价目表，让卖家清楚倍率相对的是什么价格。

**币种与汇率（决策 D16）**：统一按 1:1 结算。sub2api 按美元官方价计算 `total_cost`，本系统把 1 个余额单位直接当作 1 元人民币：

- 买家充值 1 元，sub2api 余额增加 1；
- 卖家 1 个收益单位，提现 1 元。

示例：一次请求按官方价计 `total_cost = 1`（直接调官方 API 要花 1 美元），寄售倍率 m_s = 0.3，抽佣 c = 20%：

| | 金额 |
|---|---|
| 买家付 | 1 × 0.3 × 1.2 = 0.36 元 |
| 卖家得 | 1 × 0.3 = 0.30 元 |
| 平台得 | 0.06 元 |

也就是说，按真实汇率算，买家实际支付约为官方价的 m × (1 + c) ÷ 汇率，卖家每消耗价值 1 美元的官方额度拿到 m 元。市场页和卖家门户都要把这个口径写清楚，c、D、倍率区间、回收基础倍率这些定价参数也要按这个口径来设。

## 2. 回收报价

```
m_b = 基础倍率(厂商, 订阅档位) × 等级系数(等级)
```

- 基础倍率表和等级系数由管理员维护。
- 等级来自质量检测；该厂商未开启检测时，使用检测策略中的默认等级。
- 报价有有效期（如 7 天）。到期后按最新等级重新报价：新报价不低于旧报价时自动续期；低于旧报价时需要卖家确认，确认前挂单暂停调度。
- 判定降智不改报价，直接不调度（决策 D9）。

## 3. 余额设计

```
买家充值现金 → 本系统记账 → 给 sub2api 影子用户加余额
买家调用：sub2api 实时扣影子用户余额，余额不足即拒绝
用量入账：本系统拉取 usage_logs → 记买家消费、卖家待结算收益、平台收入
冻结期满（T+N）→ 卖家可提现 → 申请提现 → 审核 → 代付打款
```

### 3.1 两个系统各管什么

| | sub2api（影子用户余额） | 本系统 |
|---|---|---|
| 角色 | 可消费余额，相当于本系统给买家充值的"预付卡" | 收款方和财务账本 |
| 负责 | 每次请求实时扣费；余额不足时拒绝请求 | 收款、退款、余额展示、账单、对账、卖家收益与提现 |
| 权威数据 | 消费：usage_logs 与实时余额 | 现金进出：充值单、退款单、账本 |
| 买家能否直接操作 | 不能，买家接触不到 sub2api | 能 |

所以：买家的钱付给本系统（本系统是收款商户），本系统记账后通过 Admin API 给影子用户加余额；之后的消费扣减完全由 sub2api 完成。本系统不只是代理充值，还是资金的记账方。卖家侧的余额（待结算、可提现、提现中）只存在于本系统，sub2api 里没有。

### 3.2 对账恒等式

```
sub2api 当前余额 = Σ 充值 − Σ 退款 − Σ sub2api 消费(actual_cost) ± Σ 人工调整
```

每日按买家核对，不平即告警。人工在 sub2api 后台改余额、加余额重复执行、用量漏记，都会在这里暴露。

### 3.3 充值

支付方式（决策 D19）：

| 方式 | 渠道接口 | 买家体验 |
|---|---|---|
| 支付宝电脑网站支付 `alipay_page` | `alipay.trade.page.pay` | 跳转支付宝收银台，付款后跳回钱包页 |
| 支付宝当面付 `alipay_f2f` | `alipay.trade.precreate` | 页面展示二维码，用支付宝扫码 |
| 微信支付 Native `wechat_native` | `POST /v3/pay/transactions/native` | 页面展示二维码，用微信扫码 |
| 人工确认 `manual` | — | 线下转账，管理员确认到账 |

商户在管理后台"支付配置"中站内配置，不使用配置文件或环境变量（决策 D21）：

- **基础设置**：支付通知地址（控制面对外地址，通知发到 `<地址>/api/payments/{alipay|wechat}/notify`，网页支付完成后跳回 `<地址>/buyer/wallet`）、对买家开放的支付方式、单笔充值上下限、支付时限、原路退回开关与期限。
- **支付宝**：应用 APPID、网关（正式 / 沙箱 / 自定义）、加签方式（公钥：支付宝公钥；公钥证书：应用公钥证书、支付宝公钥证书、支付宝根证书）、应用私钥。
- **微信支付**：AppID、商户号、商户 API 证书序列号、商户 API 私钥、APIv3 密钥、验签方式（微信支付公钥 ID 与公钥，或自动下载平台证书）。
- 私钥与 APIv3 密钥用字段加密密钥环（`crypto.keys`）加密后存放在 `payment_merchants`，保存后接口只返回"是否已设置"，修改时留空表示保持不变；审计日志不记录密钥。
- 启用的商户在保存时会用新配置构建一次客户端，私钥、公钥或证书无效时拒绝保存；"测试连接"向渠道查询一个不存在的订单，渠道返回"订单不存在"即说明签名、密钥与验签都正确。
- 配置变更约 5 秒内在 api 与 worker 生效，无需重启；配置不变时复用已有客户端（保留微信平台证书缓存）。
- 停用商户只是不再创建新订单：已有订单的通知、查单、关单、退款照常处理，避免付款后无法入账。

```
买家下单 → 创建充值单（pending，支付时限默认 30 分钟）→ 向渠道下单，保存收银台地址或二维码内容
渠道异步通知（验签）/ 主动查单 → 金额与订单一致 → 充值单 crediting，写账本交易（按充值单去重）
        → 写 sub2api_ops：给影子用户加余额，幂等键 = 充值单号 → 发送成功 → credited
```

- **到账依据**只有两个：验签通过的异步通知（`POST /api/payments/{alipay|wechat}/notify`），或主动查单的结果。前端轮询订单时距上次查单超过 5 秒会触发一次查单；worker 对待支付订单前 10 分钟每 20 秒、之后每 2 分钟查一次，弥补通知丢失。
- **金额不一致**的通知不入账，记计费异常 `payment_amount_mismatch` 由人处理。
- **超时**：超过支付时限 1 分钟仍未支付的订单向渠道关单并标记 expired；关单时发现已支付则转为入账。
- **取消后又付款**：用户取消时先向渠道关单（当面付未扫码时支付宝侧没有交易，二维码在超时前仍可能被扫）；渠道确认已支付的订单无论是否已取消、已过期都入账，worker 在支付时限后 10 分钟内继续查询已取消的订单。
- **重复通知**、通知与查单并发：按充值单状态条件更新，只入账一次；每次通知的处理结果写入 `payment_notifications`。
- 人工充值单只能由管理员确认到账；在线订单只能由渠道确认（管理员可以手动触发查单）。
- sub2api 加余额失败时由出站发送器重试，期间买家看到"到账中"；进入死信的订单标记失败待人工处理，重复的支付通知不会再次入账。

### 3.4 退款（退剩余余额）

```
暂停该买家的所有 Key（推送 Edge）→ 等进行中的请求结束、用量写入
→ 读取 sub2api 当前余额 → 调 sub2api 扣减该金额 → 记账，拆分打款明细，恢复 Key
→ 原路退回（worker 调渠道退款接口）+ 人工打款（管理员登记流水号）→ 全部明细完成后退款完成
```

- 先扣 sub2api 余额再打款，防止退款过程中余额被继续消费。
- sub2api 的扣减操作不允许余额变成负数（已确认），即使有并发消费也不会多退；扣减失败就重新读取余额再试。
- **打款拆分**（`refund_payouts`）：按充值单从新到旧，把退款金额原路退回到"原路退回期限"（默认 90 天，需不超过渠道的可退款期限）内的在线充值单，每单最多退其未退部分；人工充值、超过期限或渠道已下线的部分生成一条人工打款明细。可以在后台关闭原路退回，改为全部人工打款。
- 原路退回使用固定的退款单号（`TMF<退款号>O<充值单号>`），重复提交是幂等的：支付宝同步返回结果，微信先受理后查询结果。失败的明细管理员可以重试，或改为人工打款（释放原充值单的可退金额）。

### 3.4.1 按充值单退款（退指定金额）

买家在钱包的充值记录里、管理员在后台充值订单里，选一笔已到账的充值单输入金额退款（`refunds.kind = order`）：

```
校验：金额 ≤ 该订单未退金额（实付 − refunded_amount），且 ≤ 可退余额（sub2api 余额 − 未用完的额度包）
→ 同一事务内：生成退款单（直接进入扣减）与一条打款明细，占用订单的可退金额，入队扣减 sub2api 余额
→ 扣减成功：记账，退款进入 paying，worker 原路退回该订单（或等管理员登记人工打款）
→ 扣减失败（期间余额被用掉）：退款失败，打款明细作废（cancelled），释放订单的可退金额
```

- 不暂停 Key：只退一部分，扣减不会把余额扣成负数，余额不足时扣减失败，不会多退。
- 在原路退回期限内、渠道可用的在线订单原路退回；人工充值、超过期限、渠道已下线或关闭了原路退回时人工打款。人工打款的部分也计入该订单的 `refunded_amount`，一笔订单累计退款不超过实付金额；失败的原路退回改为人工打款时不释放。
- 与退全部余额共用"同一买家只能有一笔进行中的退款"的约束。
- 额度包原路退款（`kind = pack`）同样是先生成打款明细再扣减余额。所有预先生成的明细都要等退款进入 paying（扣减成功）后才会打款。

### 3.5 余额展示

- 买家控制台显示的"当前余额"直接读 sub2api（只读库，缓存几秒），这是实时可用的数字。
- 账单、消费明细来自本系统入账后的数据，有几分钟延迟，页面上标明"统计截至某时刻"。

### 3.6 负余额

sub2api 是先调用后扣费：请求开始前检查余额大于 0，请求完成后按实际用量扣费，扣费时余额不足也会扣成负数（已对照代码确认）。并发请求较多时，买家余额可能出现小额负数。

- 账本允许买家余额为负，下次充值先抵扣。
- 负余额期间 sub2api 会拒绝新请求，不会继续扩大。
- 申请退款时余额为负则无可退金额。

### 3.7 赠送余额（如有促销）

**第一期未实现**（没有促销赠送，账本只有 `buyer_cash`）。设计如下：sub2api 只有一个余额数字，本系统在账本中区分"现金余额"和"赠送余额"：赠送部分不可退款；消费时先扣赠送还是先扣现金由本系统规则决定（建议先扣赠送），退款上限 = 现金余额。

## 4. 账本

复式记账，每笔交易借贷平衡，按业务单号去重，只追加不修改。

| 业务 | 分录 |
|---|---|
| 买家充值 | 现金收入 ↑，买家现金余额 ↑（赠送部分记买家赠送余额） |
| 买家调用（批量入账） | 买家余额 ↓ actual_cost（按赠送、现金的扣减顺序）；卖家待结算 ↑ payout；平台收入 ↑ (actual_cost − payout) |
| 探测调用 | 平台探测成本 ↑ payout；卖家待结算 ↑ payout |
| 冻结期满 | 卖家待结算 ↓，卖家可提现 ↑ |
| 申请提现 | 卖家可提现 ↓，卖家提现中 ↑ |
| 提现到账 | 卖家提现中 ↓，现金支出 ↑ |
| 提现失败 / 驳回 | 卖家提现中 ↓，卖家可提现 ↑ |
| 买家退款 | 买家现金余额 ↓，现金支出 ↑（先扣减 sub2api 余额） |
| 人工调整 | 必须有审批记录和原因 |

其中 payout = total_cost × account_rate_multiplier（sub2api 记录的请求发生时的账号倍率），actual_cost 是 sub2api 按分组倍率向买家扣的费用。

## 5. 用量入账

**拉取**

- 按 `usage_logs.id` 增量拉取。数据库自增 id 的提交顺序不一定与 id 顺序一致，因此：
  - 只读取 `created_at` 早于当前时间 2 分钟的记录；
  - 每次从游标往前回退一段重新扫描，按 `sub2api_usage_id` 主键去重。
- sub2api 可能有用量清理任务删除历史 usage_logs，所以必须准实时拉取，本系统的 `usage_records` 和账本才是结算依据。

**归属**

| 字段 | 解析方式 |
|---|---|
| 上游 / 卖家 | `account_id` → `upstreams.sub2api_account_id` |
| 挂单 | 上游在 `created_at` 时刻有效的挂单 |
| 买家 / 买家 Key | `api_key_id` → `internal_keys` |
| 渠道 | 分组为 `tm-l-*` → direct；`tm-pool-*` → pool；探测用户 → probe；基线分组 → reference |

无法归属的记录（例如非 `tm-` 资源产生的用量）标记为 `unknown` 并告警，不进入结算。

**聚合**：按"上游 × 小时 × 渠道"汇总成 `settlement_lines`，每日生成账本分录。

## 6. 计费口径与逐次对账

原则（决策 D17）：**以 sub2api 实际产生的费用为准**。sub2api 产生了费用（写了 usage_log、扣了影子用户余额），就向买家计费、给卖家结算；sub2api 没有产生费用，就不计费。本系统不在 sub2api 之外另行减免或补扣，职责是逐条核对、能解释每一笔费用。

sub2api 对失败的调用不产生费用（见 6.1），所以"失败调用不计费"由 sub2api 保证，本系统用对账来证明。

### 6.1 各情形下 sub2api 是否产生费用

| 情形 | sub2api 的行为 | 本系统 |
|---|---|---|
| 返回错误，尚未输出任何内容（含 Edge 故障转移时失败的那几跳） | 不产生费用。已对照网关代码确认：转发出错时直接返回，不调用用量记录 | 不计费 |
| sub2api 组内切换账号：前面的账号失败，后面的账号成功 | 只有最终成功的一次产生费用 | 只按成功的那次计费，只结算成功的账号 |
| 正常完成 | 产生费用 | 计费 |
| 输出中途买家主动断开 | 标记 `ClientDisconnect`，按已产生的用量计费 | 计费，账单标注"中途断开" |
| 输出中途上游断开 | 是否产生费用待行为契约测试确认 | 跟随 sub2api：产生了就计费，没产生就不计费 |
| 成功返回但用量为 0 | 产生一条费用为 0 的记录 | 0 元 |

另外，sub2api 按"请求 ID + API key"对扣费去重（`usage_billing_dedup` 表），同一请求不会被重复扣费。

### 6.2 逐次尝试对账

**关联键**：sub2api 网关对每个请求生成一个 UUID，通过响应头 `X-Client-Request-ID` 返回（错误响应也带），并写入 `usage_logs.request_id`，格式为 `client:<UUID>`。Edge 记录每一跳拿到的这个值，就能把每次尝试和 usage_log 一一对上。

**Edge 尝试日志**（`edge_attempts`）：每一跳一条，记录买家请求 ID、买家 Key、第几跳、挂单或默认分组、sub2api 请求 ID、HTTP 状态码、是否已向买家输出、结束原因（完成 / 买家断开 / 上游错误 / 超时）、首字节时间、起止时间。

**对账规则**（准实时，每 5 分钟；另有每日全量）：

| 规则 | 条件 | 处理 |
|---|---|---|
| R1 失败但有费用 | Edge 记为失败，但存在对应的 usage_log | 按 sub2api 计费。归类原因（通常是输出中途断开），在账单中说明。如果确认是 sub2api 的计费缺陷，由管理员发起人工调整（需审批） |
| R2 成功但无费用 | Edge 记为成功完成，超过 10 分钟仍无对应 usage_log | 告警排查（可能是用量记录丢失）。按 sub2api 记录为准，不凭 Edge 推算补扣 |
| R3 无来源费用 | 存在 usage_log（买家渠道），但找不到对应的 Edge 尝试 | 按 sub2api 计费；告警并冻结相关内部 key 排查，可能是内部 key 泄露或有人绕过 Edge 直连 sub2api。确认是泄露导致的，由管理员人工调整 |
| R4 重复费用 | 同一 sub2api 请求 ID 对应多条 usage_log | sub2api 已去重扣费，正常不应出现；出现即告警排查 |
| R5 中途断开 | 结束原因为买家断开，存在 usage_log | 正常计费，账单标注"中途断开，按 sub2api 实际计费" |

探测和基线流量不经过 Edge，不参与 R3，按探测用户单独核对。

对账的目标是三者一致：Edge 的尝试记录、sub2api 的 usage_log 与扣费、本系统的账本。任何不一致都进入 `billing_anomalies` 由人处理，系统不自动退款或补扣。

### 6.3 买家和卖家看到什么

- **买家账单**逐请求展示：请求 ID、尝试过的每一跳及其状态（失败的跳标注"未产生费用"）、实际提供服务的挂单、token 数、费用、中途断开标注、人工调整记录。
- **卖家**的收益明细只来自 usage_log；自己挂单上的失败尝试只出现在测试报告和健康指标里，不产生收益。
- **卖家用量**（卖家中心"用量"与上游详情）：每个上游经平台产生的请求数（买家 / 平台检测）、token、官方价费用与收益，按日、按模型、按上游汇总并可查看逐次记录，不展示买家身份、Key 与请求内容；同时展示账号的官方订阅窗口使用率与重置时间（来自 sub2api 账号用量接口，使用率包含卖家在平台之外的使用），以及自留比例对应的暂停调度线。
- 按天统计（账单、用量、今日收益、每日检测预算）的日界由数据库会话时区 `database.time_zone` 决定，默认 Asia/Shanghai。

### 6.4 前提配置

sub2api 的用量记录是异步写入的，队列满时的行为由 `gateway.usage_record.overflow_policy` 决定。必须保持默认值 `sync`（队列满时改为同步写入），不能设为 `drop` 或 `sample`，否则成功的请求可能漏记用量。此项写入 sub2api 基线配置和兼容契约。

## 7. 对账

| 对账项 | 方法 | 频率 |
|---|---|---|
| 买家余额 | 按第 3.2 节的恒等式逐个买家核对 | 每日；不平即告警 |
| 卖家收益口径 | usage_log 中的 `account_rate_multiplier` 与 `listing_price_versions` 中当时的倍率一致 | 每日 |
| 余额调整 | `sub2api_ops` 中的加减余额操作与 sub2api 余额流水（`/admin/users/:id/balance-history`）一一对应 | 每日 |
| 用量完整性 | 本系统入账条数与 sub2api 同时段 usage_logs 条数一致 | 每小时 |
| 逐次尝试 | Edge 尝试日志与 usage_logs 按 sub2api 请求 ID 逐条核对 | 见第 6.2 节 |

**余额调整的幂等**：sub2api 的余额接口（`POST /admin/users/:id/balance`）支持 `Idempotency-Key` 请求头（有效期 24 小时）。本系统先写 `sub2api_ops`，用其 ID 作为幂等键调用；超过 24 小时仍未确认的操作，先查余额流水再决定是否重发。

## 8. 提现

- 卖家必须通过实名认证。
- 提现金额按 1:1 换算为人民币。
- 冻结期 T+N，N 不短于支付渠道的拒付和争议期，管理员可配置。
- 最低提现金额、每日次数与额度上限可配置。
- 审核：低风险自动通过，高风险进入人工审核（见第 9 节）。
- 代付通道抽象成接口，第一期接入哪个通道待定（见 [11](11-roadmap.md)）。

## 9. 资金风控

现金提现最大的风险是套现和洗钱。典型手法：用盗刷的卡充值成为买家，Key 指定自己挂的卖家，把余额消耗掉，再以卖家身份提现。

| 措施 | 说明 |
|---|---|
| 实名 | 卖家提现必须实名 |
| 冻结期 | 不短于支付渠道的拒付期 |
| 关联识别 | 买卖双方的 IP、设备、支付账号、实名信息关联时标记，关联交易的收益延长冻结或不予结算 |
| 集中度限制 | 新卖家来自单一买家指定流量的收益设上限 |
| 新买家限额 | 新买家单笔和每日充值上限 |
| 提现分级审核 | 金额、卖家信用、关联风险决定是否人工审核 |
| 盗号挂卖 | 实名 + 冻结期 + 申诉通道，被投诉的上游冻结未结算收益 |
