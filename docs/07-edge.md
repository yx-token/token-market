# 07 Edge 路由网关

## 1. 为什么需要 Edge

买家可以指定最多 5 个卖家，按顺序故障转移，并按每个卖家各自的价格付费。sub2api 在不改代码的前提下做不到：

1. **顺序无法按买家区分**：优先级是账号级的，同一账号在所有分组里优先级相同，买家甲的"A → B"与买家乙的"B → A"不能共存。分组模型路由取出的是账号集合，仍按账号优先级排序。sub2api 分组的两个兜底字段只用于"非 Claude Code 客户端"和"无效请求"，不能用于"不可用时切换到另一个分组"。
2. **价格无法按卖家区分**：一个分组只有一个售价倍率。

所以由 Edge 在 sub2api 前面做跨分组的故障转移：每个卖家一个分组（各自的倍率），Edge 依次用不同的内部 key 请求 sub2api。

Edge 是本系统唯一位于请求链路上的组件，设计上保持极简：鉴权、选路、转发、失败重试，不做计费和调度。

## 2. 买家 Key

- 格式 `tm-` + 随机串，只在创建时明文返回一次，数据库只存哈希。
- 路由类型：
  - `default`：只有一跳，指向某个默认分组；
  - `chain`：1–5 跳，每跳是一个寄售挂单，最后一跳可以是默认分组。
- 每个买家 Key 的每一跳对应一把内部 key（影子用户名下，绑定该跳的 sub2api 分组）。内部 key 按"买家 Key × 分组"创建，这样 sub2api 的 `usage_logs.api_key_id` 可以对应回具体的买家 Key。

## 3. 请求处理

```
1. 从请求中取出买家 Key：Authorization: Bearer、x-api-key、x-goog-api-key 或 ?key=
2. 查本地缓存得到路由配置；不存在或已禁用 → 401
3. 检查 Key 级限制：IP 白名单、过期时间、是否被控制面暂停
4. 读取并缓存请求体（用于重试，设置大小上限）
5. 依次尝试每一跳：
     跳过控制面下发的"跳过列表"中的挂单和处于熔断状态的挂单
     把买家 Key 替换成该跳的内部 key（放在与原请求相同的位置）
     转发到 sub2api
     成功或不可重试的失败 → 返回给买家
     可重试的失败且尚未向买家输出任何内容 → 下一跳
6. 所有跳都失败 → 返回最后一跳的错误
```

### 3.1 故障转移规则

| sub2api 返回 | 是否切换下一跳 |
|---|---|
| 503（无可用账号等） | 切换 |
| 429 | 切换 |
| 500 / 502 / 504 | 切换 |
| 连接失败、首字节超时 | 切换 |
| 400 / 401 / 403 / 404 / 413 / 422 | 不切换，原样返回 |
| 余额不足（HTTP 403，`code` 为 `INSUFFICIENT_BALANCE`，已实测） | 不切换（各跳共用同一个影子用户的余额） |
| 内容审核拦截 | 不切换 |
| 已经开始向买家输出 | **不切换**，与 sub2api 自身的规则一致 |

sub2api 在开始流式输出前出错时会返回对应的 HTTP 状态码，所以 Edge 只需要看状态码，不需要解析流内容来决定是否切换。

### 3.2 超时

- 每跳连接超时 3 秒。
- 整个请求有一个总的首字节截止时间（默认 30 秒，可配置），而不是每跳各自超时，避免 5 跳都慢时买家等待数分钟。
- 首字节之后的流式传输不设 Edge 级超时，交给 sub2api 和客户端。

### 3.3 熔断

- 以挂单为单位（所有买家共享），连续失败达到阈值后熔断一段时间，期间直接跳过；到期后放行少量请求试探。
- 熔断状态在 Edge 实例内维护，同时把失败事件上报控制面作为被动健康信号。

### 3.4 跳过列表

控制面把以下挂单推送给 Edge 直接跳过，不必先失败一次：

- 健康状态为 `degraded` 或 `unavailable`；
- 挂单已暂停或关闭；
- 卖家被风控冻结。

### 3.5 响应头

- `X-TM-Listing`：实际提供服务的挂单 ID（默认分组则为分组名）。
- `X-TM-Hop`：第几跳成功。

便于买家对账和投诉。

### 3.6 WebSocket

Codex 等客户端会用 WebSocket（如 `GET /v1/responses`、`/v1/realtime`）。Edge 只在握手阶段做故障转移，握手成功后双向透传。

## 4. 第一期支持的路径

与 sub2api 网关路径保持一致，只转发对话相关接口：

| 路径 | 用途 |
|---|---|
| `POST /v1/messages`、`/v1/messages/count_tokens` | Anthropic 协议（Claude Code） |
| `POST /v1/chat/completions` | OpenAI Chat Completions |
| `POST /v1/responses`、`/v1/responses/*`，`GET /v1/responses`（WebSocket） | OpenAI Responses（Codex） |
| `/backend-api/codex/*` | Codex 直连路径 |
| `/v1beta/models/*` | Gemini 原生协议 |
| `/antigravity/v1/*`、`/antigravity/v1beta/*` | Antigravity |
| `GET /v1/models` | 模型列表（取第一跳） |

图片、视频、语音和异步任务接口暂不开放。异步任务的结果查询必须回到创建任务的同一跳，需要额外的任务与跳的映射，放到后续。

## 5. Key 级限制

| 限制 | 在哪里执行 |
|---|---|
| IP 白名单、过期时间、启用状态 | Edge，实时 |
| 余额 | sub2api，实时（影子用户余额不足即拒绝） |
| 买家并发、RPM | sub2api 影子用户的并发与 RPM 设置 |
| Key 的花费额度、5h / 1d / 7d 限额 | 控制面按用量入账统计，超限后推送 Edge 暂停该 Key。有几分钟延迟，属于软限制 |

## 6. 配置分发

- 控制面把每个买家 Key 的路由配置（哈希、各跳的内部 key、限制、版本号）写入 Redis，并通过 pub/sub 通知 Edge。
- Edge 在本地内存中缓存配置，按版本号更新。Redis 不可用时继续使用本地缓存；控制面宕机不影响 Edge。
- Edge 冷启动时从 Redis 全量加载，加载完成前不接流量。
- 内部 key 在 Redis 和 Edge 内存中都应加密存放，Edge 持有解密密钥。
- **第三方检测临时令牌**（`tm-tp-` 开头）也走同一套配置：只有一跳，指向被测上游的探测分组（复用探测 key 的密文，附加认证数据为 `system-key:<分组>`），带截止时间；检测结束后控制面删除配置。尝试日志的 `buyer_key_id` 为 0，费用记在探测渠道，不进入买家计费对账。

## 7. 部署与可观测性

- 至少 2 个实例，置于负载均衡之后，与 sub2api 同机房，到 sub2api 使用长连接。
- 热路径不访问数据库。
- 指标：每跳的请求数、状态码、首字节时间、故障转移次数、熔断状态。
- 访问日志只记录元数据（买家 Key 前缀、路径、跳、状态码、耗时），不记录请求和响应内容。
- 对无效 Key 做限速，防止暴力枚举：单个 IP 每分钟超过 `edge.invalid_key_limit`（默认 30）次无效 Key 后，该分钟内的请求直接返回 429（每个实例独立计数）。
- 买家 IP（IP 白名单、限速）按受信任代理规则解析：只有直连方在 `edge.trusted_proxies`（负载均衡地址）中时才采信 `X-Forwarded-For`，并从右往左取第一个不受信任的地址；默认不信任任何代理，直接用连接地址，防止伪造请求头绕过白名单。
- 管理端口（`edge.admin_addr`）提供 `/healthz`（配置加载完成前返回 503）与 `/debug/vars`（expvar：请求数、各结束原因的尝试数、故障转移次数、熔断次数、无效 Key 限速次数）。

## 8. 计费与对账

Edge 不计费，计费由 sub2api 按每一跳的分组倍率完成，本系统以 sub2api 实际产生的费用为准（决策 D17）。Edge 负责留下对账证据：

- 每一跳都记录一条尝试日志，包括 sub2api 响应头 `X-Client-Request-ID` 的值、状态码、是否已向买家输出、结束原因。sub2api 把同一个值写进 `usage_logs.request_id`（`client:<UUID>`），据此逐条核对，规则见 [08](08-billing.md) 第 6 节。
- 尝试日志异步写出，不阻塞请求：先进内存队列，每秒（或满 500 条）用 `COPY` 批量写入 market 库的 `edge_attempts`；写库失败或队列满时追加到本地暂存文件（`edge.spool_dir`），每 30 秒重放。正常退出时先把队列写完。
- 投递积压或丢失会让对账出现大量"无来源计费"告警，所以投递延迟和积压量要纳入监控。
