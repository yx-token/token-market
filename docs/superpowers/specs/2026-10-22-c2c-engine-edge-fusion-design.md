# 二手 TOKEN 市场融合设计（C2C + Edge 调度 + 引擎执行）

- **状态**：已定稿（2026-10-22）
- **依据**：`c2c-system-interaction` 业务流程；产品决策：买家侧不退款；架构方案 1（Edge 调度脑 + 引擎执行臂）
- **取代/收敛**：将「闲猫为旁路模块」心智收成「本系统即二手 TOKEN 市场」；保留 Edge，不作为可删过渡层

## 1. 目标与非目标

### 目标

- 产品核心：用户出售多余账号 TOKEN 额度；买家购买后通过平台调用上游。
- 对外一个系统：管理端与 C 端统一产品面，不出现独立「闲猫插件」运营心智。
- 请求路径：买家 → **Edge（智能调度）** → **引擎（协议 / 上游 / 引擎额度）**。
- 资金：钱先进平台托管；卖家只拿**成功用量**对应收益；然后冻结 → 提现。

### 非目标（本设计明确不做）

- **买家侧任何退款**：无协商退货、无未使用余额退、无平台介入退款、无充值原路退（买家侧）。
- 将 Edge 并入引擎进程作为唯一网关（调度仍独立在 Edge，便于迭代策略）。
- 一次性物理删除 `market/` 目录（允许代码渐进合并；对外能力先统一）。

## 2. 业务模型（按 C2C 图，去掉退货）

### 2.1 商品与处置

| 类型 | 是否买家可购 | 说明 |
|------|----------------|------|
| **商品 A** 按量通道 | 是 | 卖家自定倍率 + 福利额度 M；可进市场；可选再进保障池；可勾选服务标签 |
| **商品 B** 订阅套餐 | 是 | 固定面额 + 份数；进市场；不进保障池；可勾选服务标签 |
| **平台回收** | 否（非商品） | 产能包销进保障池；与 A/B **互斥**；买家看不见「回收商品」 |

规则：

- 同一上游**同时只能一条有效处置**；回收 ↔ A/B 切换须先关闭当前处置。
- 「平台质检」标签只能由平台打；卖家可勾选服务承诺标签，不可自贴质检标。
- 质检可选：不走质检仍可上架，但无质检标签/报告。

### 2.2 主链路

```text
① 上架 → ② 下单（托管）→ ③ 使用（Edge 调度 → 引擎转发）→ ⑤ 结算（用量 → 冻结 → 提现）
```

**不做 ④ 退货。**

#### ① 上架

卖家接入上游并声明可卖模型 →（可选）平台质检 → 二选一：挂 A/B，或走平台回收。

#### ② 下单

买家选择：商品 A、商品 B、或开通保障池 → 支付进入平台托管（暂不给卖家）→ 获得使用资格。  
回收卖家不产生「被购买的订单」，收益仅来自池子吃量。

#### ③ 使用

- 买家调用（指定卖家通道或保障池）→ Edge 智能调度 → 引擎转发上游。
- 仅成功调用进入扣费/结算。
- **A**：先扣福利额度 M，超出扣余额。
- **B**：只扣包内剩余。
- **保障池 / 回收产能**：池子流量**优先**落回收号；买家付池价 D；回收卖家按 `m_b` 结算。

#### ⑤ 结算

- 成功用量入账：A/B 用 `m_s`；回收用 `m_b`。
- 冻结观察期（无买家退款争议单；冻结用于风控/对账，不服务于退货协商）。
- 卖家申请提现 → 平台审核打款。

### 2.3 平台回收（摘要）

- 按量包销、不买断账号；不预付；只对成功用量 × `m_b` 结算。
- 定价（配置项）：`m_b = min(回收基础倍率 × 等级系数, 池子成本上限)`；成本上限由保障池售价 D 与毛利/缓冲推导。
- 控本：硬封顶、需求闸门、质量门槛、同质低价优先、日/周支出上限、到期重报须确认。
- 体验：对标展示、优先吃量、进度可见、报价透明。
- 退出回收后才能再挂 A/B；降智/超预算可停收。

### 2.4 买家退款政策

**买家侧完全不能退款。**  
服务标签中若历史文案含「七天无理由全退」等，实现与运营文案须改为与本政策一致（不得承诺可退）。

## 3. 架构（方案 1）

```text
买家 ──Key /v1──► Edge（智能调度）──选定供给──► 引擎（协议/上游/引擎额度）──► 上游厂商
                      ▲                              ▲
                      │                              │
              资格 / 池子 / 倍率 / 用量事件      账号·分组入库
                      │                              │
                 业务 API（上架/托管/回收/结算/管理）
```

| 组件 | 职责 | 不负责 |
|------|------|--------|
| **Edge** | 买家 Key 鉴权；按 A/B/保障池做智能调度；发出用量/路由事件 | 人民币托管账本主存；管理端 UI |
| **引擎** | 上游协议、账号/分组、引擎侧额度扣减 | C2C 商品目录、回收报价 UX、人民币提现审核主流程 |
| **业务 API + 数据** | 上架、质检、支付托管、回收、结算提现、管理运营 | 替代引擎打上游 |

### 3.1 融合原则（去冗余）

- **保留双组件**：Edge 与引擎分工清晰，不是重复的两套「完整网关产品」。
- **收掉平行心智**：管理端不再「外挂市场二次登录」；供给账号入库引擎后由 Edge 调度，避免长期两套不可调度的账号真相。
- **目录可渐进**：`market/` 与 `backend/` 允许分步合并；对外路由与产品叙事先统一为「二手 TOKEN 市场系统」。

### 3.2 与 ADR 0001 的关系

- ADR 0001 的同仓同端口、统一管理壳仍然有效。
- 本设计修正产品重心：**市场是本体**，引擎是执行底座，Edge 是调度层。
- 买家退款相关能力按本设计冻结/移除，不按旧 C2C 图第四节实现。

## 4. 验收标准

1. 买家只需配置 **Edge** 入口即可完成模型调用。
2. 同一上游不能同时处于「有效 A/B」与「有效回收」。
3. 买家支付后不存在任何买家退款 API/入口（管理端亦无「给买家退款」主路径）。
4. 卖家收益仅来自成功用量（A/B 的 `m_s` 或回收的 `m_b`），经冻结后可提现。
5. 保障池调度接口位支持「优先吃回收产能」（策略可迭代，契约先稳定）。
6. 管理端与 C 端表现为同一产品能力，而非旁路模块。
