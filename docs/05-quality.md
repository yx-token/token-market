# 05 质量检测

质检体系已实现协议底座、参数化题库、逐项评估、等级与估价、报告和调度开关。默认 `trial`（试运行）：计算并展示新结果，旧题继续决定健康、等级、回收报价和调度；运营校准后可切换 `formal`（正式）。每条扣价或门槛规则还需独立登记校准，启用不等于已校准。设计依据见[2026-10-12 汇总调研](research/quality-inspection-2026-10-12.md)，字段、默认值、JSON 示例和预算以[数据契约](research/inspection/data-contract.md)为准。

## 1. 目标

订阅账号的主要质量问题：

- **不可用**：授权被撤销、账号被封、订阅到期、窗口耗尽。
- **能力不符或下降**：档位虚报、实际作答型号变化、推理强度不足、上下文或输出被截断。账号共用、官方信任或安全路由可能相关，但不能把“走代理必然降智”当作已证实因果。
- **性能差**：首字延迟高、输出速度慢、429 频繁（常见于卖家自己也在大量使用）。

检测结果用于三件事：决定是否调度、给回收挂单定级报价、生成卖家可查看的测试报告。

平台固定官方 `base_url`，卖家 CONNECT/SOCKS5 代理仅转发端到端 TLS，证书校验仍开启；卖家不能在这一链路上改写题目或回答。质检重点核验配置与实际服务表现，并提供 `appraisal_base × Q` 的寄售参考价；寄售倍率仍只受厂商区间限制，不新增质检价格上限。检测是抽样，不能保证没有偷换。

## 2. 信号来源

| 来源 | 内容 | 成本 | 是否受检测开关控制 |
|---|---|---|---|
| sub2api 账号状态（只读库） | `status`、`error_message`、限流与过载时间、临时不可调度原因、窗口用量快照 | 无 | 否，始终开启 |
| sub2api 用量（只读库） | 成功请求的首字延迟、耗时、输出 token 分布、`upstream_response_model` 与型号不一致记录；失败分母需结合 Edge 观测 | 无 | 否，始终开启 |
| Edge 观测 | 每跳的状态码、首字节时间、故障转移次数与错误来源；旧来源未知的失败不纳入卖家失败分母 | 无 | 否，始终开启 |
| **主动探测** | 通过探测分组向上游发测试请求 | 消耗卖家窗口额度，由平台付费 | **是** |

被动信号能发现"不可用"和"疑似降智"，但不足以确认降智，确认降智依赖主动探测加基线对照。

**证据边界**：响应型号先归一化日期别名，以同期基线的官方自动路由作为观察白名单；`upstream_model_mismatch=true` 只作复核提示。A02/A03/A12 当前均为展示项，未批准“重扣”系数。自报身份受 Claude Code、Codex、Antigravity 注入影响，不作真伪判据。输入计数只比较同型号、同入口、同接入配置、输入内容一致的请求；Claude 总输入含缓存创建与读取，OpenAI 缓存 token 已包含在输入内。多步题使用各自真实上轮响应，动态步骤不要求两侧输入计数相等。

所有功能仅由 token-market 通过 sub2api 现有 Admin API、用户 API、网关、只读数据库和配置实现，任何阶段都不修改 sub2api。契约与集成测试迁移基线为 v0.2.14；网关分析已先看当前 HEAD `3a6fd1c9d`，再与标签核对，差异见[只读网关对照](research/inspection/sub2api-rewrites.md)。不可取得的 `OpenAI-Model` 头、Claude 订阅核档等标“无法判定；依赖 sub2api，后续处理”。

## 3. 厂商检测开关

管理员在后台按厂商（可细化到接入方式）配置检测策略，修改后约 1 分钟内生效，无需重启。

| 配置项 | 说明 |
|---|---|
| `enabled`（是否检测） | 上架检测之外的检测总开关。关闭后不做恢复复测、追加探测、卖家手动复测；上架检测始终执行，豁免现有美元日预算 |
| `scheduled_enabled`（是否定时检测） | 依赖总开关。开启后按周期探测 |
| `interval_minutes` / `jitter_minutes` | 定时检测周期和随机抖动 |
| `suites` | 启用哪些测试套件 |
| `models` | 测哪些模型 |
| `daily_budget_usd` | 每个上游每天的探测预算（按官方价计） |
| `thresholds` | 判定阈值和置信度 |
| `auto_pause` | 确认降智后是否自动不调度；关闭则只告警 |
| `default_grade` | 不检测时使用的默认等级（用于回收报价） |
| `item_parallelism` | 题目单元并发上界，默认 4；账号实际并发与全局槽另行限制 |
| `full_triggers` | 完整质检触发原因，默认 onboarding/appeal/admin；恢复有失败项时升级完整 |
| `token_budgets` | 按 full/quick 覆盖每侧输入、输出硬预算；空对象使用 inspection 默认值 |

**开关组合的效果**

| 是否检测 | 是否定时检测 | 会发生的主动探测 |
|---|---|---|
| 关 | — | 只有上架检测（首次配置必做，决策 D18）与管理员手动检测。之后降智只能由被动信号发现为"疑似"，通知管理员，不自动暂停 |
| 开 | 关 | 上架检测；事件触发的检测：降智后的恢复复测、被动信号异常后的追加探测、卖家手动复测、管理员手动检测 |
| 开 | 开 | 以上全部 + 周期检测 |

**动态生效**

- 策略存数据库并带版本号，worker 每轮读取最新策略；修改后通知调度器立即重算；每次探测记录使用的策略版本。
- 策略可以按厂商（`auth_type` 为空）或按接入方式配置，接入方式级策略优先；新建接入方式级策略时以厂商级策略为模板。
- 开启定时检测时，各上游的首次探测在一个周期内随机分散，避免同时打满。
- 关闭检测不会改变上游当前的健康状态，已经被判为降智而暂停的上游，保持暂停，并在管理后台列出，由管理员决定恢复或重新开启检测。

**单个上游覆盖**：管理员可以对某个上游强制开启或关闭检测（例如重点观察可疑账号），可设到期时间。

**独立开关**：后台系统设置单独编辑 `settings.inspection`，不混入 `platform`。`mode` 默认 `trial`（试运行），新项、Q 和估价只展示，等级、回收报价与调度仍走旧判定；运营校准后由管理员切 `formal`（正式），新题参与正式评估，原 22 道内置题按原题面跳过。调度开关 `inspection.scheduling.enabled` 独立且默认 `false`；试运行以及正式模式关闭开关时，相同输入的规划器输出与旧版一致，既有健康暂停仍有效。规则的 enabled、calibrated、校准登记、系数与阈值在后台“质检项”页独立编辑；未校准规则不扣价、不确认新门槛。检测总开关的现有例外继续保留，不能用美元日预算豁免绕过 token、窗口和时限约束。

## 4. 测试套件与质检项

### 4.1 当前题库与套件

| 套件 | 测什么 | 判分方式 |
|---|---|---|
| `availability` | 汇总旧题请求是否正常返回 | 限流、平台与题目配置错误不作卖家不可用 |
| `latency` | 汇总旧题首字延迟、输出速度 | 输出 P50/P95 与 TPS；保留旧 suites 结构 |
| `iq` | 算术、逻辑、格式等静态题 | exact、contains、regex、numeric、choice、json_keys 六种旧判分器 |
| `reasoning` | 固定题与 effort 的推理量 | 可靠 usage 优先；必要时按 token 估算并标记，缺失为未知 |
| `long_context` | 旧单针信息检索 | 旧题展开字符约定，保留回退兼容，不把字符数当作 token 上限 |

旧选择器只选择 `iq/reasoning/long_context` 中适用的启用题；只启用可用/延迟时用 iq 题作请求载体但不计智力分。`availability/latency` 复用请求汇总，不是额外两套请求。新选择器支持 `inspection_authenticity/capability/context/function/output/performance` 六种新套件，执行时自动加入，不修改已保存策略 suites。已有 active 新题时，trial 新批次按 full/quick 计算；没有新题或全部下线时仍 legacy，已排队 legacy 走旧路径。每题仍按平台、型号、模式和状态筛选。不存在代码沙箱判分。

**题库**

- 私有，定期轮换，卖家不可见，避免被针对性优化。
- 每次检测测全部适用题目，不抽样：启用套件下所有使用中的题，且题目的适用厂商、适用模型包含本次检测的厂商和模型（为空表示不限）。针对某个模型出的题（例如只考 gpt-6-astra）设置适用模型即可。
- 每道题可记录 IRT（项目反应理论）难度和区分度字段；这些字段不代表题目已经完成实测标定。
- 管理后台维护题目、判分规则、适用厂商与适用模型，以及标定数据；支持 check_key、request、generator、modes，并按模板和版本查看。
- 管理后台「上游」页的「检测明细」可以查看每次检测的逐题结果：题目、是否通过、耗时、token 与回答片段（前 500 字符），有基线对照时并列显示基线账号的结果。卖家看到的报告仍是脱敏的，不含题目与回答。
- 管理后台「检测 → 检测记录」汇总所有上游的检测：
  - 「检测记录」按厂商、模型、触发原因、结论与日期筛选，列出每次检测的结论、按套件的答题情况、智力相对分、推理强度、首字延迟与输出速度，「明细」里有各项指标、按套件汇总与逐题结果。默认不含基线账号的同批次对照检测，可在触发原因中选「基线对照」单独查看。
  - 「按题统计」列出每道题在筛选范围内的被测通过率、基线通过率、错误数、平均耗时与平均推理 token，「各次结果」查看这道题在每次检测中的回答。单独通过率低不能证明区分度高，还须比较健康基线与受控降档的差异。
- 题库越大，单次检测越慢、越贵：基线账号同批次也答适用题，被测与基线同时发送；full/quick 按单元并行，多步在各自账号内顺序执行，受 token 硬预算与固定截止时间限制。legacy 保留旧单元串行与预算超支仅告警的语义。

**探测请求的形态**：通过与买家相同的网关入口发送受支持请求，不伪装 Claude Code 绕过网关改写。两侧入口、注入、协议、型号映射与 effort 应一致。

### 4.2 参数化题库与判分器

已实现八类 Go 生成器：斑马谜题、骑士与无赖、寄存器机、AIME 式数学（同余计数、末三位、二进制串、格点路径）、代码输出预测、字符串变换与日期算术、中英自由写作可验证约束、长上下文（多针、多跳、聚合、首尾、联想针）。工具语义、多轮约束、完整输出、中文大写金额、诚实弃权以少量静态或半参数化题起步。当前内置目录含 31 条新增稳定键定义：修正后的题库 25 条，加缓存、图片、PDF、权限、边界、thinking 六条；旧新版本行并存但新选择器排除已替代键。A08 暂不放事实题，诚实弃权归 D07.honesty。

派发前按固定顺序预生成实例，seed 使用 `HMAC(平台密钥, batch_id | item_id | instance_idx | generator_version)`，双侧拿到相同初始题面，记录版本与哈希；多步在同一账号内有序执行，后续步骤使用该账号真实上轮响应。Go 同 seed 同哈希，不假定与 Python 随机序列一致。斑马默认 5×5（待运营校准），可配置到 6×6，双求解器验证唯一解；数学用枚举与公式两路验证，自由写作约束题按题面独立解析，验证参考文本、其他合法文本和逐项违例；生产服务不执行生成代码，测试中可用 `python3 -I` 做交叉验证。

新增十一种判分器：`answer_tag`、`fields_exact`、`set_exact`、`lines_alias`、`constraints`、`json_schema`、`tool_calls`、`abstain`、`full_output`、`num_list`、`accept_reject`。统一输出 `pass / partial / flags`，精确规定最终答案格式，不猜回答里的最后一个数字；输入计数比对由引擎按配对计算。服务端不运行模型生成的代码，也不需要模型复述推理过程。题目不含网络安全攻击、生物、毒理、前沿模型训练、越狱或注入串。

保留全部 22 道旧内置题及其状态、题面与 suite。试运行继续由旧题驱动现有判定，正式模式新程序按原题面识别并跳过旧题，回退程序仍有旧题可选。新题使用新 suite，内置同步仅补缺，不复活管理员停用项；新统计按“模板 + 版本 + 难度档”聚合，逐项证据按 `item_id + instance_idx + step` 配对。

质检目录在 `internal/inspection` 中注册，数据库仅在 `inspection.check_overrides` 保存覆盖值。配置证据不直接扣价，当前不自动核定官方 SKU；门槛项独立触发 `degraded/unavailable` 或上架不通过，不作为系数为零的扣价项。下表候选阈值必须完成 A/A、阳性对照并单独登记 calibrated/calibration_note 后才影响正式结果。

## 5. 降智判定

### 5.1 基线对照

平台为每个模型族自备至少一个基线账号（干净 IP 的官方账号），与被测上游**在同一时段跑同一批题**。评分用相对值：

```
相对分 = 被测上游的得分 / 基线账号的得分（同题、同时段）
```

同期同题对照用于降低官方全局波动与题目难度变化的干扰，不能据此证明已经排除全部混杂因素。

两侧按同一实例同时发送，正式模式基线按平台、型号、接入方式、档位和负载选择，试运行保留旧基线选择兼容；实际网关注入与配置一致性仍须运营核对。旧题保留近七天至少五个有效样本的历史通过率及缺基线时 0.95 的兼容估计；正式新题只使用同期有效配对，不使用默认概率进入 SPRT 或扣价。官方全局归因另按同模板、版本、难度参数与入口切分基线历史。

快检未执行的项可以继承最近正式完整质检中同型号、同一冻结 inspection 配置、七天以内且已实际应用的证据，保留原 checked_at 并标 source=history；本次 inconclusive/fail 等已有观测不被历史覆盖。历史继承不能证明修复，也不把未执行项显示为本次已测。

### 5.2 统计判定

LLM 输出有随机性，不能因为一两道题答错就判降智。采用序贯检验（SPRT）：

- 当前按每题基线通过率构建两种假设：H0 为被测通过率 = 0.9 × 基线通过率（正常），H1 为 0.7 × 基线通过率（降智），具体阈值在检测策略中配置。展示的相对分不是直接拿来逐题计算似然比的观测。
- 测完全部适用题目后计算似然比，越过上界判"降智"，越过下界判"正常"；介于两者之间时，偏向 H1 判"疑似"，否则判"无法判定"。

### 5.3 判定结果

| 结果 | 条件 |
|---|---|
| `normal` | 检验接受 H0 |
| `suspected` | 被动信号异常，或检验未越过边界但偏向 H1 |
| `degraded` | 检验接受 H1，且归因为账号本身 |
| `unavailable` | 可用性测试失败，或 sub2api 账号状态为 error |
| `inconclusive` | 测完全部适用题目仍无法判定 |

### 5.4 门槛、扣价与等级

SPRT 仅决定严重降智门槛，配对 McNemar 仅决定智力扣价，两者使用同一组配对和剔除规则。任一侧拒答、截断、限流或平台错误时两侧一起剔除智力样本，仍保留对应功能/输出/可用证据。无显著差异不等于等效，样本不足不扣价；`relative_score` 继续展示。

仅已校准的有效扣价项合成 `Q`：能力组取推理、智力、上下文、完整输出中的最差；功能组乘 thinking、工具、图片/PDF、缓存，下限 0.7，Schema/多轮与工具合并为同一功能面只扣一次；可用组乘成功率与异常 429，下限 0.6；性能取 TTFT/TPS 中最差，范围 [0.85,1.05]。四组乘积限制在 [0.5,1.05]。不适用、未测、无法判定与未校准项不参与系数，覆盖不足标 provisional；无任何已校准的有效扣价观测时 Q 为 null，不能伪造“通过”。确认门槛时不进入 Q，也不展示有效估价。

等级分界为 S≥1.02、A≥0.93、B≥0.82、C≥0.65，其余 D；S 另需近三十天无门槛与七天可用率≥99.5%。等级采用 ±0.02 滞回，非门槛降级须连续两次有效确认；首次上架缺 S 所需历史时最高 A。试运行仍用旧相对分定级与原回收报价。质检估价、回收报价和保障池影响见[计费 §质检估价](08-billing.md)与[调度设计](06-scheduling.md)，不改变寄售厂商价格区间。

## 6. 归因

判定降智后先归因，再决定处置，保证对卖家公平：

| 现象 | 归因 | 处置 |
|---|---|---|
| 同一代理下多个上游近期同时降智 | 代理疑似 | 提示更换代理后复测；相关性不是代理导致降智的证明 |
| 有有效基线且未命中官方全局/同代理规则 | 账号 | 依据检测策略处置并展示报告；不宣称已经排除全部外部因素 |
| 基线账号也一起下降 | 官方全局 | 不处罚任何上游，管理后台显示厂商级事件 |
| 没有有效基线 | 未知 | 不把证据不足写成账号确认降智 |

试运行继续原有总体历史归因；正式模式按同题、版本、难度参数、型号、接入方式与档位切分基线历史逐题比较，避免换题库后把题型难度差误判成官方全局下降。时段性波动应先校准，现阶段不宣称已实现独立的官方时段策略识别。

## 7. 处置与恢复

| 判定 | 处置 |
|---|---|
| `degraded`（账号原因，试运行策略 `auto_pause` 开启或正式确认门槛） | 不调度；Edge 跳过该挂单；生成测试报告；安排恢复复测 |
| `degraded`（试运行，`auto_pause` 关闭） | 继续调度，后台显示异常与报告 |
| `suspected` | 继续调度，提高探测频率（在预算内） |
| `unavailable` | 不调度，测试报告提示重新授权等建议；本期不新增信用处罚 |
| 官方全局事件 | 不处置单个上游 |

**恢复**：恢复复测按 30 分钟、1 小时、2 小时……逐步拉长间隔，上限 12 小时。连续两次判定正常后恢复调度。降智期间该上游没有被调度，自然没有收益，不另做结算折扣。

平台当前没有主动卖家通知机制，影响通过报告“对你的影响”告知，本期不新增消息服务、宽限赔付或结算折扣。正式模式恢复必测 `last_failed_checks`，有失败项时升级完整质检；每项必须取得本次 pass，历史继承、无法判定和未测不能证明修复。暂停后的第一次通过仍保留失败项，第二次有效正常才清除并恢复；上架完整检测沿用一次正常即可的例外。预算跳过、中断或无有效观测须退避重排。

**执行与超时**：排队的检测按批次（被测上游与基线账号同批出题）在 worker 后台并发执行（`worker.probe_concurrency`），不占用质量调度单轮的时限。超时在系统设置中调整，修改后对之后开始的批次生效：

| 设置 | 默认 | 作用 |
|---|---|---|
| `probe_request_timeout_seconds` | 180 秒 | 单次请求（一道题发给被测上游或基线账号）的超时，超时按请求失败计入判定 |
| `probe_batch_timeout_minutes` | 30 分钟 | 整批的总时限，不能短于单次请求超时；超过后这次检测记为失败，不出结论 |

检测失败（超时、出错、无有效可用观测，或零成功且样本证据不足）时不改变健康状态；上架记为不通过并说明可重试，申诉回到待处理，恢复按退避重排。已有独立可靠的 confirmed 门槛证据时照常处置。worker 停止时进行中的批次放回队列：full/quick 保留完成实例续跑，legacy 保留旧结果清空重跑语义，但题面、截止和累计用量不重置。进程异常退出的新批次可重新排队续跑，截止到期后失败；旧无截止记录保留原超时兼容。

`probe_runs.mode/deadline_at` 保存 full/quick 独立截止；执行快照冻结完整 inspection 设置、策略、预算、模板与实例，设置修改只影响之后开始的 run，第三方等待和续跑也保留本次设置。每批只在被测 run 存一份快照，基线按 batch_id 读取同一份。账号信号量容量取 min(策略 item_parallelism、设置账号上限默认 2、账号当前下发到 sub2api 的实际并发)，基线同理；全局上限在持主锁的 worker 中控制。429/529 归 `rate_limited`，单次重试最多等待 30 秒，更长 Retry-After 不重试本题并保留等待信息；不作主动探针可用失败。预期 400 归 `expected_reject`，拒答独立；网关并发、探测余额不足与 `claude_code_version_too_old` 归 `platform`，不归因卖家。

协议按型号注册表转换参数：Claude 新型号 adaptive + output_config.effort、旧 Sonnet/Haiku 4.5 用 budget_tokens，Gemini 3 用 thinkingLevel、2.5 用 thinkingBudget，OpenAI 用 reasoning.effort。型号例外须明确，不能笼统认为全部 Claude 5.x 都不支持 disabled。Claude 推理量优先读输出明细，缺失才用总输出减可见文本 token 并标“估算”，不再按 thinking 字符；OpenAI reasoning 为 output 子集，Gemini thoughts 单列，Grok reasoning 不包含在 output 中，预算不得重复相加。没有可靠观测标未知。

## 8. 卖家测试报告

卖家可以在门户里查看自己每个上游的测试报告，了解是否降智、有哪些问题。

**报告列表**：每次检测一条，包括时间、触发原因（上架 / 定时 / 恢复复测 / 手动 / 管理员）、判定结果、对调度的影响。

**报告详情**：按配置、真伪、能力、功能、可用与性能分组展示质检项，含结论、Q、组系数、等级、质检估价、门槛、归因与影响；缺观测不能填造示例值。只有旧 summary.suites 的历史报告仍按旧形态正常渲染。

| 内容 | 示例 |
|---|---|
| 总体结论 | 正常 / 疑似降智 / 确认降智 / 不可用 / 无法判定 |
| 各套件结果 | 智力相对分 72%（基线 100%），样本 40 题，置信度 95% |
| 推理强度 | 推理 token 中位数为基线的 35% |
| 性能 | 首字延迟 P50 / P95、输出速度 |
| 账号信息 | 可读订阅档位、隐私状态与窗口快照；未知/未核验明确标注，不冒充官方核档 |
| 归因 | 账号本身 / 代理 / 官方全局 |
| 对你的影响 | 已暂停调度，预计下次复测时间 |
| 建议 | 检查是否在其他地方大量使用该账号；重新授权；开启隐私设置 |
| 趋势 | 近 30 天智力相对分与异常次数；生产可用率采用可归因分母，不把成功用量当作全量请求 |
| 修复后预计等级 | 按缺陷消除后的 Q=1 与当前历史估计；需复测确认，S 仍需持续可用与无门槛历史 |

**不展示**：题目内容和标准答案、基线账号信息、代理 IP、精确的判定阈值。

**手动复测**：卖家可以发起复测（例如重新授权之后），每天限次，发起前提示会消耗窗口额度。仅在该厂商开启检测时可用。

**申诉**：卖家对 degraded/unavailable 报告及已实际应用且系数小于 1 的扣价项可申诉，管理员审核后复测、维持或撤销。复测不因美元日预算而跳过，仍受本次 token 与时限约束；未校准候选项不冒充已经扣价。

**买家能看到什么**：市场页只展示脱敏摘要：健康状态、等级徽章、关键项、质检估价、上次检测时间和局限声明“检测是抽样，不能保证没有偷换”，不展示报告详情。

逐项显示结果、对价格/调度的影响与安全建议，明确未测/不适用/无法判定，不展示内部证据定位。试运行标“试运行，不影响价格”。卖家发布页与上游详情展示摘要、估价和卖家倍率相对估价的偏离度；缺基准为“未配置”，无有效 Q 或确认门槛为“暂不估价”，不限制卖家倍率。管理员逐题页展示 check_key、usage、flags、stop_reason、实例哈希与版本，并按 item_id + instance_idx + step 配对。

`summary.suites` 的 availability（success/total）、latency（ttft_p50_ms/ttft_p95_ms/output_tps）、iq（relative_score/samples/confidence）、reasoning（ratio_to_baseline）层级与类型保留；新增 `checks/quality_factor/appraisal/gates/inspection_mode/mode`。`summary.checks` 与 `quality_verdicts.checks` 同构，为 check_key→结果对象，status 明确区分 pass/warning/fail/inconclusive/not_applicable/not_run；字段与脱敏规则见[数据契约 §5](research/inspection/data-contract.md#5-checksgates-与-summary)。旧报告缺新增字段正常渲染，原 impact 字段继续保留。

## 9. 第三方检测

在平台自有探测之外，可以把上游交给第三方检测站做模型身份检测（决策 D20）。第一个接入的是 BazaarLink Probe API（`POST /api/probe/run` 提交、`GET /api/probe/run/{id}` 轮询）：向被测端点发送约 80–90 道探针题，判断端点背后是否为声明的模型（家族与具体型号）、有没有伪装或掉包，并给出行为警告。

2026-10-12 抓取为 86 项（84 标准 + 2 可选），不等于每次接口固定执行全部项。逐项保留/改造/删除的取舍见[汇总调研](research/quality-inspection-2026-10-12.md)。第三方历史准确率不是本次端点“未换模”的概率，也不能替代本平台的同入口基线与参数校准。

**流程**

1. 平台探测完成后，如果策略为本次检测类型（上架检测、定时检测、管理员检测、申诉复测等）配置了第三方检测，且检测站已启用，检测记录进入 `third_party` 状态，为每个检测站生成一条 `third_party_checks`。平台探测判定为不可用时不再提交。
2. worker 为每条检测生成一个 Edge 临时令牌（`tm-tp-` 开头）：只路由到该上游的探测分组，截止时间后 Edge 拒绝，检测结束后立即撤销。把 Edge 对外地址（`edge.public_url` + `/v1`）与令牌交给检测站。检测站的请求经 Edge 访问被测账号，和平台探测一样计入探测成本（channel = probe）。
3. 按检测站的频率限制排队提交（BazaarLink 同一出口 IP 每小时 30 次，后台可设更低的上限），遇到限流按 `Retry-After` 等待；每 20–30 秒轮询一次，超过"等待结果上限"记为超时。
4. 全部检测站结束后合并结论并处置（与平台探测共用一套处置与恢复逻辑）。

**结论折算**

| 检测站结论 | 归类 | 折算（策略可配置） |
|---|---|---|
| clean_match、clean_match_family_only | 身份一致 | 正常 |
| clean_match_submodel_mismatch | 型号不一致 | 默认判为疑似 |
| plain_mismatch | 身份不一致 | 默认判为降智 |
| spoof_behavior_induced、spoof_selfclaim_forged | 疑似伪装 | 默认判为降智 |
| ambiguous、insufficient_data、检测失败、超时 | 证据不足 | 不影响结论 |

最终结论取平台探测与第三方折算结论中更严重的一项；由第三方结论导致的降智归因为"账号本身"，报告中给出"第三方检测站判定身份不一致"的建议，卖家可以申诉复测。检测站返回的被测端点原始回答、响应头、提交者 IP 等不保存，报告中只保留判定、置信度、探针统计、警告与检测站报告链接。

第三方结果同时产出 third_party 质检项；正式身份不符门槛须规则 enabled 且 calibrated，试运行继续旧折算口径。证据不足继续不影响结论，也不能作为恢复通过。等待态的 `{"internal": Assessment}` 保存内部 checks/Q/gates 与冻结 inspection 设置，`finishRun` 兼容缺新字段的旧记录，合并保留内部证据。

**接入新的检测站**：在 `internal/quality/thirdparty` 中实现 `Provider`（提交、轮询、把结果归类为上表五类之一）并登记，后台"第三方检测"页面会自动出现对应配置。

**注意**：真实检测站只接受公网 https 地址，`edge.public_url` 必须对外可访问；开发环境用替身时需要在后台打开"允许 http / 内网地址"。

## 10. 探测成本

- 探测请求经 sub2api 计费到平台的探测用户。它真实消耗了卖家的额度，所以**卖家照常获得收益**，在账本中记为平台探测成本。
- 当前每次检测开始前检查该上游当天的探测花费，达到策略中的 `daily_budget_usd` 后当天跳过并记录；上架、管理员与申诉检测豁免美元日预算。旧题会测完全部适用项，所以日预算可能超出一次检测的成本。
- 探测用户的 sub2api 余额不足时请求会被拒绝（403），会被误判为不可用。所以执行排队的检测前先确认探测用户余额可用，不足时排队充值、检测顺延到下一轮；余额低于 20 时自动补足 100。
- 新长上下文只在完整质检中执行，定时快检不包含；试运行旧题仍由管理员配置的 suites 决定适用范围。

### 10.1 强度与硬预算

默认“上架完整质检 + 每日一次快检”，可按厂商覆盖，申诉/管理员默认完整，恢复按上次失败项补测或升级完整。以下为单型号、每侧约量，不是运营实测或 SLA；多步每次 HTTP 算一次请求，low 加测也计入，双侧总量约为两倍。

| 模式 | 每侧请求 | 每侧预计输入 / 输出（含推理） | 每侧输入 / 输出硬上限 | 预计时长 / 独立截止 |
|---|---:|---|---|---|
| 快检 | 约 25 | 30–50K / 80–100K tokens | 80K / 160K tokens | 约 6–14 分钟 / 20 分钟 |
| 完整 | 约 90 | 1.0–1.1M / 300–450K tokens | 1.3M / 640K tokens | 约 30–50 分钟 / 75 分钟 |

组成与假设见[数据契约 §7](research/inspection/data-contract.md#7-请求token-与时长预算)。31 条新增内置在全部适用且相关规则启用时 full 每侧 90 次、quick 25 次：原题库 73、补充探针 7、high 锚定 low 加测 10；A15 默认无请求。Codex 跳过完整输出、部分平台跳过 PDF，规则关闭也减少题量，跳过不补题。普通高档题复用型号、计数、推理量与性能证据；完整包含 8K/32K/128K 多子类与独立上下文边界探针，不能靠有限长度检索认证全部 1M。多型号权限、指纹登记、扩样与恢复追加必须重新预留预算，不暗算在 90 次内。

正式恢复若失败项含 D13/D04，完整计划额外加入 100 个短连通性新样本，全部适用默认每侧 190 次；仍受同一 token 预算、200 个实例、32MiB 快照和截止时间限制。样本下限超出可容纳范围时明确失败并退避重排，不自动放大额度，也不以不足样本恢复。统计从门槛后的新证据开始，真实恢复时长与成本待运营校准。

开跑前读取只读窗口快照或现有 Admin API 的 passive 用量；仅在快照明确显示余量不足时顺延并记录原因；未知时照常执行并在结果/报告标“窗口余量未知”，上架、申诉与管理员检测不因未知阻塞，仍受 token 硬预算、单请求超时及 run 截止时间约束，不调用 active 查询访问真实厂商。派发前预留输入与最大输出，按 usage 修正，到预算停止新派发。Codex OAuth 删除输出上限，现有网关不能可靠限制单请求时，只能停止后续请求，在途请求可能超出预留，记“依赖 sub2api，后续处理”，不承诺精确费用封顶。

试运行另计用于旧判定的 22 道旧题请求（依当前适用配置），旧 availability/latency 复用旧题结果，不重复计费；旧题预算仅告警，新题执行硬上限，新题预算/时限失败不能推翻已完成旧结论。第三方最多 86 项属于单独预算阶段，纳入探测成本，不属于自有 90/25 次。美元日预算豁免不能绕过窗口与超时约束；legacy 超支只告警以保持旧流程兼容。真实完整质检 p95 < 截止时间 70% 为校准目标，当前待运营校准；替身不能证明真实成本或时长。

## 11. 被动异常检测

不消耗额度，持续运行：

- **同组对比**：同型号上游的首字延迟明显偏离同行时标记为 `suspected`，开启检测时触发追加探测。调度按等级/价格优先，生产样本是观测数据，不能当作随机对照实验；成功率与输出分布扩展须采用一致分母与入口。
- **模型声明不一致**：`upstream_model_mismatch` 为真的比例超过阈值。
- **账号状态**：sub2api 把账号标成 error、频繁限流或过载，转为 `unavailable` 或降低评分。
- **Edge 观测**：某挂单作为第 1 跳时频繁触发故障转移。

D13 使用 edge_attempts 建立可归因生产分母，不能把仅记录成功的 usage_records 当作全量成功率；旧错误来源未知、平台/配置错误、限流、跳过和买家取消排除。D04 只统计已核实窗口未耗尽且复查仍有余量的异常探针 429，窗口未知不扣价。D10 使用 usage_records 的同型号各上游分位数；至少四个同行，样本不足改用同期配对基线，基线不授予同行 P25/P75 奖励。现有被动预警继续工作，归一化前的型号不一致信号只作触发线索。

## 12. 数据契约与上线校准

完整契约见[新增列与安全默认值](research/inspection/data-contract.md#2-新增列)、[请求与生成器 JSON](research/inspection/data-contract.md#3-请求与生成器-json)、[inspection 设置键](research/inspection/data-contract.md#6-inspection-设置键)。`0022` 覆盖 probe_items、probe_results、probe_runs、quality_verdicts、upstreams、upstream_quality_state、vendor_configs 与 detection_policies，`0023` 仅补 edge_attempts.error_class；不另建逐项结果表。目录在代码中注册，数据库仅保存覆盖值；未知观测使用 NULL 或“未测”，不以零冒充采集成功。

回退只回程序、不回迁移：仅增列、放宽约束与安全默认值，不删除旧题，不改变现有策略的 models/suites；新题新 suite 确保旧选择器只能选到旧题。`inspection` 独立于旧程序整包保存的 `platform`；保留 summary.suites、原 impact 与第三方旧等待记录。正式开关由管理员校准后启用，调度开关另行决定。

上线前至少两个同型号、同入口、同档位健康基线做 A/A，跨时段、新会话检查逐项输入计数相等、参数接受规则、推理量方差与误报。阳性对照使用 high/medium/low、同家族小一档模型、通道可用的输出上限减半；Codex OAuth 删除输出上限，此干预不适用。每题族每难度档先生成 30–50 个候选，保留独立留出集，优先选择 high 通过约 85–95%、降档单调且成本合理的题；题面、版本或网关配置改变后重新建立历史。

登记 D06 配对对数比与估算规则、McNemar 显著性/多项比较/分档、SPRT 配对剔除清单以及 D13 分母。研究中“10–20 锚定题”依赖方差，原 40 精选题的功效不适用于 25 次快检；样本不足记无法判定而不扣价。只有 A/A 一致、阳性对照可检出、真实基线无意外 4xx、Claude 推理 token 可采集、时长/成本与阈值通过备案后才切正式。上述真实账号项目全部**待运营校准**，本轮无真实厂商调用，也不承诺校准工具已经实现。
