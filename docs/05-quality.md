# 05 质量检测

本文区分当前已实现的检测流程与“质检体系升级”的后续设计。标为**升级规划**的质检项、配置、题库、估价与页面尚未实现；阶段二修正协议与误判，阶段三新题只记录，阶段四才接入质检定级。设计依据见[2026-10-12 汇总调研](research/quality-inspection-2026-10-12.md)，字段、默认值、JSON 示例和预算以[数据契约](research/inspection/data-contract.md)为准。

## 1. 目标

订阅账号的主要质量问题：

- **不可用**：授权被撤销、账号被封、订阅到期、窗口耗尽。
- **能力不符或下降**：档位虚报、实际作答型号变化、推理强度不足、上下文或输出被截断。账号共用、官方信任或安全路由可能相关，但不能把“走代理必然降智”当作已证实因果。
- **性能差**：首字延迟高、输出速度慢、429 频繁（常见于卖家自己也在大量使用）。

检测结果用于三件事：决定是否调度、给回收挂单定级报价、生成卖家可查看的测试报告。

平台固定官方 `base_url`，卖家 CONNECT/SOCKS5 代理仅转发端到端 TLS，证书校验仍开启；卖家不能在这一链路上改写题目或回答。升级规划重点核验配置与实际服务表现，并提供 `appraisal_base × Q` 的寄售参考价；寄售倍率仍只受厂商区间限制，不新增质检价格上限。质量结果不等于“绝对未换模型”的认证。

## 2. 信号来源

| 来源 | 内容 | 成本 | 是否受检测开关控制 |
|---|---|---|---|
| sub2api 账号状态（只读库） | `status`、`error_message`、限流与过载时间、临时不可调度原因、窗口用量快照 | 无 | 否，始终开启 |
| sub2api 用量（只读库） | 成功请求的首字延迟、耗时、输出 token 分布、`upstream_response_model` 与型号不一致记录；失败分母需结合 Edge 观测 | 无 | 否，始终开启 |
| Edge 观测 | 每跳的状态码、首字节时间、故障转移次数 | 无 | 否，始终开启 |
| **主动探测** | 通过探测分组向上游发测试请求 | 消耗卖家窗口额度，由平台付费 | **是** |

被动信号能发现"不可用"和"疑似降智"，但不足以确认降智，确认降智依赖主动探测加基线对照。

**升级规划的证据边界**：响应型号先归一化，应用日期别名与官方回退/自动路由白名单；不能直接处罚 `upstream_model_mismatch=true`。自报身份受 Claude Code、Codex、Antigravity 注入影响，不作真伪判据。输入计数只比较同型号、同入口、同接入配置、输入内容一致的请求；Claude 总输入含缓存创建与读取，OpenAI 缓存 token 已包含在输入内。多步题使用各自真实上轮响应，动态步骤不要求两侧输入计数相等。

所有功能仅由 token-market 通过 sub2api 现有 Admin API、用户 API、网关、只读数据库和配置实现，任何阶段都不修改 sub2api。契约与集成测试迁移基线为 v0.2.14；网关分析已先看当前 HEAD `3a6fd1c9d`，再与标签核对，差异见[只读网关对照](research/inspection/sub2api-rewrites.md)。不可取得的 `OpenAI-Model` 头、Claude 订阅核档等标“无法判定；依赖 sub2api，后续处理”。

## 3. 厂商检测开关

管理员在后台按厂商（可细化到接入方式）配置检测策略，修改后约 1 分钟内生效，无需重启。

| 配置项 | 说明 |
|---|---|
| `enabled`（是否检测） | 上架检测之外的检测总开关。关闭后不做恢复复测、追加探测、卖家手动复测；上架检测始终执行，豁免现有美元日预算 |
| `scheduled_enabled`（是否定时检测） | 依赖总开关。开启后按周期探测 |
| `interval_minutes` / `jitter_minutes` | 定时检测周期和随机抖动 |
| `suites` | 启用哪些测试套件 |
| `models` | 测哪些模型 |
| `daily_budget_usd` | 每个上游每天的探测预算（按官方价计） |
| `thresholds` | 判定阈值和置信度 |
| `auto_pause` | 确认降智后是否自动不调度；关闭则只告警 |
| `default_grade` | 不检测时使用的默认等级（用于回收报价） |

**开关组合的效果**

| 是否检测 | 是否定时检测 | 会发生的主动探测 |
|---|---|---|
| 关 | — | 只有上架检测（首次配置必做，决策 D18）与管理员手动检测。之后降智只能由被动信号发现为"疑似"，通知管理员，不自动暂停 |
| 开 | 关 | 上架检测；事件触发的检测：降智后的恢复复测、被动信号异常后的追加探测、卖家手动复测、管理员手动检测 |
| 开 | 开 | 以上全部 + 周期检测 |

**动态生效**

- 策略存数据库并带版本号，worker 每轮读取最新策略；修改后通知调度器立即重算；每次探测记录使用的策略版本。
- 策略可以按厂商（`auth_type` 为空）或按接入方式配置，接入方式级策略优先；新建接入方式级策略时以厂商级策略为模板。
- 开启定时检测时，各上游的首次探测在一个周期内随机分散，避免同时打满。
- 关闭检测不会改变上游当前的健康状态，已经被判为降智而暂停的上游，保持暂停，并在管理后台列出，由管理员决定恢复或重新开启检测。

**单个上游覆盖**：管理员可以对某个上游强制开启或关闭检测（例如重点观察可疑账号），可设到期时间。

**升级规划的独立开关**：`settings` 新键 `inspection` 下的 `mode` 默认 `trial`（试运行），新项、Q 和估价只展示，等级、回收报价与调度仍走旧判定；运营校准后由管理员切 `formal`（正式）。调度开关 `inspection.scheduling.enabled` 独立且默认 `false`，试运行时输出与旧版一致；正式模式调度开关关闭时，相同输入的规划器输出与现状一致，既有健康暂停仍有效。检测总开关的现有例外继续保留，不能用日预算豁免绕过新 token、窗口和时限约束。

## 4. 测试套件与质检项

### 4.1 当前题库与套件

| 套件 | 测什么 | 判分方式 |
|---|---|---|
| `availability` | 汇总所发请求是否正常返回 | 状态码与错误分类；当前普通请求失败仍可能包含限流 |
| `latency` | 汇总首字延迟、输出速度 | 输出 P50/P95 与 TPS；尚未按新 D10 系数定价 |
| `iq` | 算术、逻辑、格式等静态题 | 当前仅有 exact、contains、regex、numeric、choice、json_keys 六种判分器 |
| `reasoning` | 固定题与 effort 的推理量 | 当前读已支持的 usage；缺失时的 thinking 字符估计是待修缺陷，不能据此声称新 Claude 推理为零 |
| `long_context` | 单针信息检索 | 展开约定字符长度的干扰文本，不能把字符数当作 token 上限 |

当前执行器只选择 `iq/reasoning/long_context` 中适用的启用题；只启用可用/延迟时用 iq 题作请求载体但不计智力分。`availability/latency` 来自这些请求的汇总，不是额外两套请求。工具语义、图片/PDF、多轮与完整 JSON Schema 校验属于升级规划，当前没有代码沙箱判分。

**题库**

- 私有，定期轮换，卖家不可见，避免被针对性优化。
- 每次检测测全部适用题目，不抽样：启用套件下所有使用中的题，且题目的适用厂商、适用模型包含本次检测的厂商和模型（为空表示不限）。针对某个模型出的题（例如只考 gpt-6-astra）设置适用模型即可。
- 每道题可记录 IRT（项目反应理论）难度和区分度字段；这些字段不代表题目已经完成实测标定。
- 管理后台维护题目、判分规则、适用厂商与适用模型，以及标定数据。
- 管理后台「上游」页的「检测明细」可以查看每次检测的逐题结果：题目、是否通过、耗时、token 与回答片段（前 500 字符），有基线对照时并列显示基线账号的结果。卖家看到的报告仍是脱敏的，不含题目与回答。
- 管理后台「检测 → 检测记录」汇总所有上游的检测：
  - 「检测记录」按厂商、模型、触发原因、结论与日期筛选，列出每次检测的结论、按套件的答题情况、智力相对分、推理强度、首字延迟与输出速度，「明细」里有各项指标、按套件汇总与逐题结果。默认不含基线账号的同批次对照检测，可在触发原因中选「基线对照」单独查看。
  - 「按题统计」列出每道题在筛选范围内的被测通过率、基线通过率、错误数、平均耗时与平均推理 token，「各次结果」查看这道题在每次检测中的回答。单独通过率低不能证明区分度高，还须比较健康基线与受控降档的差异。
- 题库越大，单次检测越慢、越贵：基线账号同批次也要答全部题目，题目逐道执行，总时长受系统设置中的"质量检测总时限"约束。

**探测请求的形态**：通过与买家相同的网关入口发送受支持请求，不伪装 Claude Code 绕过网关改写。两侧入口、注入、协议、型号映射与 effort 应一致。

### 4.2 升级规划：参数化题库与判分器

阶段三移植八类 Go 生成器：斑马谜题、骑士与无赖、寄存器机、AIME 式数学（同余计数、末三位、二进制串、格点路径）、代码输出预测、字符串变换与日期算术、中英可验证约束、长上下文（多针、多跳、聚合、首尾、联想针）。工具语义、多轮约束、完整输出、中文大写金额、诚实弃权以少量静态或半参数化题起步。

派发前按固定顺序预生成实例，seed 使用 `HMAC(平台密钥, batch_id | item_id | instance_idx | generator_version)`，双侧拿到相同初始题面，记录版本与哈希；多步在同一账号内有序执行，后续步骤使用该账号真实上轮响应。Go 同 seed 同哈希，不假定与 Python 随机序列一致。斑马默认 5×5（待运营校准），可配置到 6×6，双求解器验证唯一解；数学用枚举与公式两路验证，自由写作约束题按题面独立解析，验证参考文本、其他合法文本和逐项违例；生产服务不执行生成代码，测试中可用 `python3 -I` 做交叉验证。

新增十一种判分器：`answer_tag`、`fields_exact`、`set_exact`、`lines_alias`、`constraints`、`json_schema`、`tool_calls`、`abstain`、`full_output`、`num_list`、`accept_reject`。统一输出 `pass / partial / flags`，精确规定最终答案格式，不猜回答里的最后一个数字；输入计数比对由引擎按配对计算。服务端不运行模型生成的代码，也不需要模型复述推理过程。题目不含网络安全攻击、生物、毒理、前沿模型训练、越狱或注入串。

保留全部 22 道旧内置题及其状态、题面与 suite。试运行继续由旧题驱动现有判定，正式模式新程序按原题面识别并跳过旧题，回退程序仍有旧题可选。新题使用新 suite，内置同步仅补缺，不复活管理员停用项；新统计按“模板 + 版本 + 难度档”聚合，逐项证据按 `item_id + instance_idx + step` 配对。

### 4.3 升级规划：有名称的质检项

配置项用于核定 SKU 与基准倍率，不能把档位重新核定当作成色扣价；门槛项独立触发 `degraded/unavailable` 或上架不通过，不作为系数为零的扣价项。

| 类别 | 质检项与判定口径 | 处置 |
|---|---|---|
| 配置 | A01 订阅档位：仅展示令牌可读声明；Claude 当前无法官方核档 | 未核验不冒充已通过；用于选择基准档位 |
| 配置 | A04 型号权限：每个上架型号一次短请求 | 主型号无权限为上架门槛 |

| 配置 | A06 effort：实际可用档位及推理量响应度 | 标注实测档位；量不随档位变化转 D06 |

## 5. 降智判定

### 5.1 基线对照

平台为每个模型族自备至少一个基线账号（干净 IP 的官方账号），与被测上游**在同一时段跑同一批题**。评分用相对值：

```
相对分 = 被测上游的得分 / 基线账号的得分（同题、同时段）
```

同期同题对照用于降低官方全局波动与题目难度变化的干扰，不能据此证明已经排除全部混杂因素。

当前逐题先请求基线再请求被测，历史基线优先使用该题近七天至少五个有效样本；无基线时旧判定仍有 0.95 的估计。**升级规划**改为双侧同时发送，基线匹配同型号、同接入方式、同档位与网关配置，按负载选择；新题既无同批基线也无合格历史时记“无法判定”，不使用旧默认概率进入 SPRT 或扣价。

### 5.2 统计判定

LLM 输出有随机性，不能因为一两道题答错就判降智。采用序贯检验（SPRT）：

- 当前按每题基线通过率构建两种假设：H0 为被测通过率 = 0.9 × 基线通过率（正常），H1 为 0.7 × 基线通过率（降智），具体阈值在检测策略中配置。展示的相对分不是直接拿来逐题计算似然比的观测。
- 测完全部适用题目后计算似然比，越过上界判"降智"，越过下界判"正常"；介于两者之间时，偏向 H1 判"疑似"，否则判"无法判定"。

### 5.3 判定结果

| 结果 | 条件 |
|---|---|
| `normal` | 检验接受 H0 |
| `suspected` | 被动信号异常，或检验未越过边界但偏向 H1 |
| `degraded` | 检验接受 H1，且归因为账号本身 |
| `unavailable` | 可用性测试失败，或 sub2api 账号状态为 error |
| `inconclusive` | 测完全部适用题目仍无法判定 |

### 5.4 升级规划：门槛、扣价与等级

SPRT 仅决定严重降智门槛，配对 McNemar 仅决定智力扣价，两者使用同一组配对和剔除规则。任一侧拒答、截断、限流或平台错误时两侧一起剔除智力样本，仍保留对应功能/输出/可用证据。无显著差异不等于等效，样本不足不扣价；`relative_score` 继续展示。

正式模式将四组系数合成 `Q`：能力组取推理、智力、上下文、完整输出中的最差；功能组乘 thinking、工具、图片/PDF、缓存，下限 0.7；可用组乘成功率与异常 429，下限 0.6；性能取 TTFT/TPS 中最差，范围 [0.85,1.05]。四组乘积限制在 [0.5,1.05]。不适用、未测与无法判定为中性系数，并披露覆盖不足，不能伪造“通过”。门槛触发时不进入 Q，也不展示有效估价。

等级分界为 S≥1.02、A≥0.93、B≥0.82、C≥0.65，其余 D；S 另需近三十天无门槛与七天可用率≥99.5%。等级采用 ±0.02 滞回，非门槛降级须连续两次有效确认；首次上架缺 S 所需历史时最高 A。试运行仍用旧相对分定级与原回收报价。质检估价、回收报价和保障池影响见[计费 §质检估价](08-billing.md)与[调度设计](06-scheduling.md)，不改变寄售厂商价格区间。

## 6. 归因

判定降智后先归因，再决定处置，保证对卖家公平：

| 现象 | 归因 | 处置 |
|---|---|---|
| 同一代理下多个上游近期同时降智 | 代理疑似 | 提示更换代理后复测；相关性不是代理导致降智的证明 |
| 有有效基线且未命中官方全局/同代理规则 | 账号 | 依据检测策略处置并展示报告；不宣称已经排除全部外部因素 |
| 基线账号也一起下降 | 官方全局 | 不处罚任何上游，管理后台显示厂商级事件 |
| 没有有效基线 | 未知 | 不把证据不足写成账号确认降智 |

当前归因对基线近期/历史通过率作总体比较；升级规划按同题、版本、难度与入口切分历史逐题比较，避免换题库后把题型难度差误判成官方全局下降。时段性波动应先校准，现阶段不宣称已实现独立的官方时段策略识别。

## 7. 处置与恢复

| 判定 | 处置 |
|---|---|
| `degraded`（账号原因，且策略 `auto_pause` 开启） | 不调度；Edge 跳过该挂单；生成测试报告；安排恢复复测 |
| `degraded`（`auto_pause` 关闭） | 继续调度，后台显示异常与报告 |
| `suspected` | 继续调度，提高探测频率（在预算内） |
| `unavailable` | 不调度，测试报告提示重新授权等建议；本期不新增信用处罚 |
| 官方全局事件 | 不处置单个上游 |

**恢复**：恢复复测按 30 分钟、1 小时、2 小时……逐步拉长间隔，上限 12 小时。连续两次判定正常后恢复调度。降智期间该上游没有被调度，自然没有收益，不另做结算折扣。

平台当前没有主动卖家通知机制，影响通过报告“对你的影响”告知，本期不新增消息服务、宽限赔付或结算折扣。升级后恢复必测 `last_failed_checks`，快检未覆盖上次失败项不能视为已恢复；跳过预算或中断后须重新安排复测。

**执行与超时**：排队的检测按批次（被测上游与基线账号同批出题）在 worker 后台并发执行（`worker.probe_concurrency`），不占用质量调度单轮的时限。超时在系统设置中调整，修改后对之后开始的批次生效：

| 设置 | 默认 | 作用 |
|---|---|---|
| `probe_request_timeout_seconds` | 180 秒 | 单次请求（一道题发给被测上游或基线账号）的超时，超时按请求失败计入判定 |
| `probe_batch_timeout_minutes` | 30 分钟 | 整批的总时限，不能短于单次请求超时；超过后这次检测记为失败，不出结论 |

检测失败（超时或出错）时不改变上游的健康状态，但依赖这次检测的流程要能继续：上架检测记为不通过（卖家可以重新检测），申诉回到待处理，恢复复测按退避重新安排。worker 停止时进行中的批次放回队列，重启后从头执行；进程异常退出遗留的"执行中"记录，超过总时限 5 分钟后记为失败。

**升级规划**：`probe_runs.mode/deadline_at` 保存每次 full/quick 的独立截止，开始时固化，不受执行中修改设置影响；`legacy` 仍兼容旧时限。中断保留完成实例与版本，只补未完成结果。题目单元并行、账号内多步有序，账号信号量容量取 min(策略 item_parallelism、设置账号上限默认 2、账号当前下发到 sub2api 的实际并发)，基线同理；全局上限在 token-market 持主锁的 worker 中控制。429/529 归 `rate_limited` 退避，不作主动探针可用失败；预期 400 归 `expected_reject`；拒答独立；网关并发、探测余额不足与 `claude_code_version_too_old` 归 `platform`，不归因卖家。

协议按型号注册表转换参数：Claude 新型号 adaptive + output_config.effort、旧 Sonnet/Haiku 4.5 用 budget_tokens，Gemini 3 用 thinkingLevel、2.5 用 thinkingBudget，OpenAI 用 reasoning.effort。型号例外须明确，不能笼统认为全部 Claude 5.x 都不支持 disabled。Claude 推理量优先读输出明细，缺失才用总输出减可见文本 token 并标“估算”，不再按 thinking 字符；OpenAI reasoning 为 output 子集，Gemini thoughts 单列，Grok reasoning 不包含在 output 中，预算不得重复相加。没有可靠观测标未知。

**报告列表**：每次检测一条，包括时间、触发原因（上架 / 定时 / 恢复复测 / 手动 / 管理员）、判定结果、对调度的影响。

**报告详情**：当前已保存结论、相对分、推理量比例、性能、可读档位、归因与影响。下表同时列出升级补充内容，缺观测不能填造示例值。

| 内容 | 示例 |
|---|---|
| 总体结论 | 正常 / 疑似降智 / 确认降智 / 不可用 / 无法判定 |
| 各套件结果 | 智力相对分 72%（基线 100%），样本 40 题，置信度 95% |
| 推理强度 | 推理 token 中位数为基线的 35% |
| 性能 | 首字延迟 P50 / P95、输出速度 |
| 账号信息 | 可读订阅档位；升级补充隐私设置、5h / 周窗口剩余，未知/未核验明确标注 |
| 归因 | 账号本身 / 代理 / 官方全局 |

**不展示**：题目内容和标准答案、基线账号信息、代理 IP、精确的判定阈值。

**手动复测**：卖家可以发起复测（例如重新授权之后），每天限次，发起前提示会消耗窗口额度。仅在该厂商开启检测时可用。

**申诉**：当前卖家对 degraded/unavailable 报告可申诉，管理员审核，必要时用更大样本复测。升级规划将可申诉范围扩到确认的扣价项。

**买家能看到什么**：市场页只展示摘要，包括健康状态标识、智力分档位（如 A / B / C）、近 24 小时和 7 天的可用率，不展示报告详情。

**升级规划的质检报告**：按配置、真伪、能力、功能、可用与性能分组，逐项给出结果、证据摘要、对价格/调度的影响与建议；同时显示 Q、等级、质检估价、上次检测时间、未测/不适用/无法判定项与修复后的预计等级。试运行明确标“试运行，不影响价格”。市场卡片与卖家发布页只展示摘要、估价和卖家倍率相对估价的偏离度，不限制卖家倍率。

`summary.suites` 的 availability（success/total）、latency（ttft_p50_ms/ttft_p95_ms/output_tps）、iq（relative_score/samples/confidence）、reasoning（ratio_to_baseline）层级与类型保留；新增 `checks/quality_factor/appraisal/gates/inspection_mode/mode`。`summary.checks` 与 `quality_verdicts.checks` 同构，为 check_key→结果对象，status 明确区分 pass/warning/fail/inconclusive/not_applicable/not_run；字段与脱敏规则见[数据契约 §5](research/inspection/data-contract.md#5-checksgates-与-summary)。旧报告缺新增字段正常渲染，原 impact 字段继续保留。

## 9. 第三方检测

在平台自有探测之外，可以把上游交给第三方检测站做模型身份检测（决策 D20）。第一个接入的是 BazaarLink Probe API（`POST /api/probe/run` 提交、`GET /api/probe/run/{id}` 轮询）：向被测端点发送约 80–90 道探针题，判断端点背后是否为声明的模型（家族与具体型号）、有没有伪装或掉包，并给出行为警告。

2026-10-12 抓取为 86 项（84 标准 + 2 可选），不等于每次接口固定执行全部项。逐项保留/改造/删除的取舍见[汇总调研](research/quality-inspection-2026-10-12.md)。第三方历史准确率不是本次端点“未换模”的概率，也不能替代本平台的同入口基线与参数校准。

**流程**

1. 平台探测完成后，如果策略为本次检测类型（上架检测、定时检测、管理员检测、申诉复测等）配置了第三方检测，且检测站已启用，检测记录进入 `third_party` 状态，为每个检测站生成一条 `third_party_checks`。平台探测判定为不可用时不再提交。
2. worker 为每条检测生成一个 Edge 临时令牌（`tm-tp-` 开头）：只路由到该上游的探测分组，截止时间后 Edge 拒绝，检测结束后立即撤销。把 Edge 对外地址（`edge.public_url` + `/v1`）与令牌交给检测站。检测站的请求经 Edge 访问被测账号，和平台探测一样计入探测成本（channel = probe）。
3. 按检测站的频率限制排队提交（BazaarLink 同一出口 IP 每小时 30 次，后台可设更低的上限），遇到限流按 `Retry-After` 等待；每 20–30 秒轮询一次，超过"等待结果上限"记为超时。
4. 全部检测站结束后合并结论并处置（与平台探测共用一套处置与恢复逻辑）。

**结论折算**

| 检测站结论 | 归类 | 折算（策略可配置） |
|---|---|---|
| clean_match、clean_match_family_only | 身份一致 | 正常 |
| clean_match_submodel_mismatch | 型号不一致 | 默认判为疑似 |
| plain_mismatch | 身份不一致 | 默认判为降智 |
| spoof_behavior_induced、spoof_selfclaim_forged | 疑似伪装 | 默认判为降智 |
| ambiguous、insufficient_data、检测失败、超时 | 证据不足 | 不影响结论 |

最终结论取平台探测与第三方折算结论中更严重的一项；由第三方结论导致的降智归因为"账号本身"，报告中给出"第三方检测站判定身份不一致"的建议，卖家可以申诉复测。检测站返回的被测端点原始回答、响应头、提交者 IP 等不保存，报告中只保留判定、置信度、探针统计、警告与检测站报告链接。

升级规划明确第三方身份不符的门槛条件，证据不足继续不影响结论；等待态的 `{"internal": Assessment}` 一起保存内部 checks/Q/gates，`finishRun` 兼容没有这些字段的旧记录，合并时不能丢失新证据。

**接入新的检测站**：在 `internal/quality/thirdparty` 中实现 `Provider`（提交、轮询、把结果归类为上表五类之一）并登记，后台"第三方检测"页面会自动出现对应配置。

**注意**：真实检测站只接受公网 https 地址，`edge.public_url` 必须对外可访问；开发环境用替身时需要在后台打开"允许 http / 内网地址"。

## 10. 探测成本

- 探测请求经 sub2api 计费到平台的探测用户。它真实消耗了卖家的额度，所以**卖家照常获得收益**，在账本中记为平台探测成本。
- 当前每次检测开始前检查该上游当天的探测花费，达到策略中的 `daily_budget_usd` 后当天跳过并记录；上架、管理员与申诉检测豁免美元日预算。旧题会测完全部适用项，所以日预算可能超出一次检测的成本。
- 探测用户的 sub2api 余额不足时请求会被拒绝（403），会被误判为不可用。所以执行排队的检测前先确认探测用户余额可用，不足时排队充值、检测顺延到下一轮；余额低于 20 时自动补足 100。
- 升级规划的长上下文只在完整质检中执行，定时快检不包含；当前旧题仍由管理员配置的 suites 决定适用范围。

### 10.1 升级规划：强度与硬预算

默认“上架完整质检 + 每日一次快检”，可按厂商覆盖，申诉/管理员默认完整，恢复按上次失败项补测或升级完整。以下为单型号、每侧约量，不是运营实测或 SLA；多步每次 HTTP 算一次请求，low 加测也计入，双侧总量约为两倍。

| 模式 | 每侧请求 | 每侧预计输入 / 输出（含推理） | 每侧输入 / 输出硬上限 | 预计时长 / 独立截止 |
|---|---:|---|---|---|
| 快检 | 约 25 | 30–50K / 80–100K tokens | 80K / 160K tokens | 约 6–14 分钟 / 20 分钟 |
| 完整 | 约 90 | 1.0–1.1M / 300–450K tokens | 1.3M / 640K tokens | 约 30–50 分钟 / 75 分钟 |

组成与假设见[数据契约 §7](research/inspection/data-contract.md#7-请求token-与时长预算)。普通高档题复用型号、计数、推理量与性能证据；完整包含 8K/32K/128K 多子类与独立上下文边界探针，不能靠有限长度检索认证全部 1M。多型号权限、扩样与恢复追加必须重新预留预算，不暗算在 90 次内。

开跑前读取只读窗口快照或现有 Admin API 的 passive 用量；仅在快照明确显示余量不足时顺延并记录原因；未知时照常执行并在结果/报告标“窗口余量未知”，上架、申诉与管理员检测不因未知阻塞，仍受 token 硬预算、单请求超时及 run 截止时间约束，不调用 active 查询访问真实厂商。派发前预留输入与最大输出，按 usage 修正，到预算停止新派发。Codex OAuth 删除输出上限，现有网关不能可靠限制单请求时，只能停止后续请求，在途请求可能超出预留，记“依赖 sub2api，后续处理”，不承诺精确费用封顶。

试运行还须另计用于旧判定的 22 道旧题请求（依当前适用配置），旧 availability/latency 复用旧题结果，不重复计费；第三方最多 86 项属于单独预算阶段，纳入探测成本，不属于自有 90/25 次。美元日预算豁免不能绕过窗口与超时约束；full/quick 执行 token 硬上限，legacy 预算超支只告警以保持旧流程兼容。真实完整质检 p95 < 截止时间 70% 是阶段三目标，当前待运营校准；替身不能证明真实成本或时长。

## 11. 被动异常检测

不消耗额度，持续运行：

- **同组对比**：同型号上游的首字延迟明显偏离同行时标记为 `suspected`，开启检测时触发追加探测。调度按等级/价格优先，生产样本是观测数据，不能当作随机对照实验；成功率与输出分布扩展须采用一致分母与入口。
- **模型声明不一致**：`upstream_model_mismatch` 为真的比例超过阈值。
- **账号状态**：sub2api 把账号标成 error、频繁限流或过载，转为 `unavailable` 或降低评分。
- **Edge 观测**：某挂单作为第 1 跳时频繁触发故障转移。

升级规划的 D13/D04 必须建立生产请求分母，不能把仅记录成功的 usage_records 当作全量成功率；排除平台错误与已耗尽窗口的 429，再结合 edge_attempts。D10 对同行不足四个的型号改用配对基线。现有被动预警继续工作，归一化前的型号不一致信号只作触发线索。

## 12. 升级规划的数据契约与上线校准
