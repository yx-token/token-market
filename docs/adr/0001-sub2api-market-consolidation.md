# ADR 0001：以 sub2api 为底座吸收市场能力

- **状态**：已接受
- **日期**：2026-10-19
- **议题**：是否把 token-market 功能并入 sub2api，以及是否立刻拆除双系统胶水

## 背景

token-market 是闲置额度交易所；sub2api（契约基线 v0.2.14）负责网关、账号托管、实时计费。当前刻意 **不修改 sub2api 源码**，通过 Admin/User API、出站队列 `sub2api_ops`、影子用户与 Edge 驱动引擎。

现在要「基于 sub2api 增加目前项目的全部功能」。

## 决策

1. **改造宿主 = 完整 sub2api 代码树**（先拿到社区全量，再叠加市场代码）。不在「只有适配层、没有引擎源码」的仓库里做终态产品。
2. **市场代码只增量添加**：新建 `market/`（及必要配置），**不删、不裁剪**社区 `backend/` / `frontend/` / `deploy/` 等原有目录；跟社区升级时以整树 merge / 搬迁为主。
3. **后台与市场前端保留本产品视觉与交互风格**（现 `token-market/web`：闲置TOKEN / xianmao 体系、买家中心、卖家中心、运营控制台）。迁入宿主后落在 `market/web`，**不以社区 `frontend/` 换皮或重做后台**；社区前端可继续随社区树保留（运维/对照），但不作为本产品对卖家/买家/运营的主 UI。
4. **采用 strangler（绞杀）合并，不 big-bang。** 现网 `token-market` 仓库过渡期仍可发版，代码按模块迁入 sub2api 宿主。
5. **前期保留** 双系统边界、出站队列、影子用户桥接——便于跟社区版本合并，并隔离计费内核风险。
6. **少改 sub2api 原文件**：禁止先改网关扣费 / OAuth 刷新 / usage 入账等内核；确需改动时单独登记并尽量上游化。
7. **终态可选收敛**：稳定后再评估进程内调用、拆除影子用户（仅当接受硬 fork 时）。
8. **资金域最后动**：人民币账本、活动包、退款提现不作为第一批迁入对象。

## 后果

### 正向

- 可继续跟社区 sub2api 升级（整包或 cherry-pick），冲突面可控。
- 每阶段都有可回滚边界；现网 token-market 可持续发版。
- 改造与现有 CI/e2e 兼容，不立刻推翻架构文档中的映射表。

### 负向

- 过渡期仍有异步中间态与对账成本。
- 「目录合并」不等于「架构已简化」——团队需接受阶段性双轨。
- 若中途改成硬改内核，本 ADR 需修订，并重估升级策略。

## 否决方案

| 方案 | 否决原因 |
|---|---|
| 立刻去掉出站队列 + 影子用户并改写计费内核 | 回归面过大，且与「方便搬社区代码」目标冲突 |
| 仅把前端迁到 sub2api、后端仍外挂且无接口治理 | 无结构收益，增加部署混乱 |
| 用社区 `frontend/` 替换本产品后台/市场 UI | 丢掉已定品牌与交互；与「保留我们前端风格」冲突 |
| 一天切单库单进程 | 资金与路由风险不可接受 |
