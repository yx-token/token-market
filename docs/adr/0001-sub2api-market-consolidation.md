# ADR 0001：以 sub2api 为底座吸收市场能力

- **状态**：已接受
- **日期**：2026-10-19
- **议题**：是否把 token-market 功能并入 sub2api，以及是否立刻拆除双系统胶水

## 背景

token-market 是闲置额度交易所；sub2api（契约基线 v0.2.14）负责网关、账号托管、实时计费。当前刻意 **不修改 sub2api 源码**，通过 Admin/User API、出站队列 `sub2api_ops`、影子用户与 Edge 驱动引擎。

现在要「基于 sub2api 增加目前项目的全部功能」。

## 决策

1. **采用 strangler（绞杀）合并，不 big-bang。**
2. **前期保留** 双系统边界、出站队列、影子用户桥接——主要为了能跟社区版本合并/搬迁，并隔离计费内核风险。
3. **少改 sub2api 原文件**：市场能力以独立模块落入（同仓或同部署），优先扩新目录，禁止先改网关扣费内核。
4. **终态可选收敛**：当市场模块稳定且跟上游策略改为硬 fork 后，再评估把 Admin HTTP 换成进程内调用、再评估去掉影子用户。
5. **资金域最后动**：人民币账本、活动包、退款提现不作为第一批内嵌对象。

## 后果

### 正向

- 可继续跟社区 sub2api 升级（整包或 cherry-pick），冲突面可控。
- 每阶段都有可回滚边界；现网 token-market 可持续发版。
- 改造与现有 CI/e2e 兼容，不立刻推翻架构文档中的映射表。

### 负向

- 过渡期仍有异步中间态与对账成本。
- 「目录合并」不等于「架构已简化」——团队需接受阶段性双轨。
- 若中途改成硬改内核，本 ADR 需修订，并重估升级策略。

## 否决方案

| 方案 | 否决原因 |
|---|---|
| 立刻去掉出站队列 + 影子用户并改写计费内核 | 回归面过大，且与「方便搬社区代码」目标冲突 |
| 仅把前端迁到 sub2api、后端仍外挂且无接口治理 | 无结构收益，增加部署混乱 |
| 一天切单库单进程 | 资金与路由风险不可接受 |
