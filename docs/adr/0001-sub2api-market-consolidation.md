# ADR 0001：以 sub2api 为底座吸收市场能力

- **状态**：已接受（2026-10-19 再修订产品形态）
- **日期**：2026-10-19
- **议题**：是否把 token-market 功能并入 sub2api，以及前后端如何分工

## 背景

token-market（闲猫）是闲置额度交易所；sub2api（契约基线 v0.2.14）负责网关、账号托管、实时计费。

目标表述：**在 sub2api 之上增量做闲猫**。管理端用 sub2api 原壳，闲猫运营是增量；C 端仍是闲猫市场。

## 决策

1. **改造宿主 = 本仓库根目录（原 idlicat 覆盖旧过渡仓）**，内含完整社区 [sub2api](https://github.com/Wei-Shaw/sub2api) 代码树，再叠加顶层 `market/`。
2. **产品形态（终态 / 2026-10-19）：**
   - **管理端 = 社区 `frontend/`**：sub2api 原壳，地址 `/engine/admin/...`。闲猫运营在侧栏「闲猫市场」。
   - **C 端 = `market/web` `/`**：市场 / 买家 / 卖家。
   - **`/admin` 与 `/console`**：跳进上述管理端。已登录闲猫则换发引擎会话，不再二次登录。
3. **市场后端**仍以 `market/` 增量为主（Edge、挂单、质检、人民币账本等）；引擎内核少改，过渡期可保留出站队列/影子用户。
4. **采用 strangler，不 big-bang。** 现网 `token-market` 过渡期可发版。
5. **资金域最后动**（专项验收前不切生产资金）。
6. **Git 远程保持现状**（不强制改名）。

## 明确纠正的旧理解

| 错误做法 | 正确做法 |
|---|---|
| 闲猫 Console 当主管理端、sub2api 外挂 | sub2api 原壳为主，闲猫只做增量 |
| 双入口（闲猫控制台 vs 引擎页） | 只保留 sub2api 管理端；`/admin`、`/console` 都进这里 |
| 「目录拷进宿主」就算合并完成 | 合并 = 单管理端 + 闲猫页能用同一套登录 |

## 后果

### 正向

- 运营只进一套管理端（sub2api 壳，闲猫风）。
- C 端闲置 TOKEN 体验独立，不被社区用户门户皮肤带偏。
- 仍可跟社区 sub2api 升级（冲突集中在 `frontend` 样式/导航与 `market/`）。

### 负向

- 改社区 `frontend` 皮肤会与上游 frontend 升级冲突，需把闲猫主题收敛到可维护的样式层。
- 过渡期仍可能双轨 API（market-api + sub2api admin），需后续换票/BFF。

## 配套约束

- 公网 www → `market/web`（C 端）；管理域 → 改造后的 sub2api `frontend/`。
- 过渡仓退役条件见实施计划。

## 否决方案

| 方案 | 否决原因 |
|---|---|
| 用社区默认皮肤做终态管理端 | 不符合「按闲猫风格改 sub2api」 |
| 用社区 frontend 替换 C 端市场/买家/卖家 | C 端必须是闲置 TOKEN |
| 立刻拆掉出站队列并硬改计费内核 | 回归面过大 |
| 一天切单库单进程 | 资金与路由风险不可接受 |
